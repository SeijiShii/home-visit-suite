# manual-sync — 操作マニュアルを最新化する

仕組み側（生成・型・陳腐化検知・検査）はすべて自動化済みで、**このスキルが担うのは本文の日本語だけ**。
仕組みの仕様は `docs/wants/12_操作マニュアル.md` が SoT。

## 起動時にまずやること

```bash
cd pwa && npm run manual:check
```

出力がそのまま作業リストになる。対象の優先順位は次のとおり。

1. **エラー**（`✖`）— sources のパス切れ・参照切れ。放置するとビルドが壊れるので最優先で直す
2. **stale**（`sources が変更されています`）— 実装が変わったのに本文が追随していない
3. **draft**（`本文が未執筆です`）— まだ書かれていない
4. **未撮影スクリーンショット** — 本文が固まってから撮る

引数でページや画面が指定されていればそれだけを対象にする。指定がなければ上の順で全件を処理する。

## 1 ページを書く手順

### 手順 1: 対象ページの sources を読む

frontmatter の `sources` に挙がっているファイル（実装 + `docs/wants/NN`）を**必ず実際に読む**。
CODEMAP の説明や記憶で書かない。マニュアルの誤りは利用者が実機で気づくまで発見されないため、
推測で書いた一文は不具合報告より質が悪い。

読むときに拾うもの:

- 画面上に実際に出るボタン・項目の**文言**（i18n catalog `pwa/src/i18n/ja/index.ts` が正）
- 操作の**前提条件**（ロール、画面幅、チェックアウトの有無など）と、条件を満たさないときの見え方
- **失敗したときに何が起きるか**（エラー表示・確認ダイアログ・取り消せるかどうか）

### 手順 2: 本文を書く

読者は**アプリの利用者**であり、開発者ではない。

- 実装用語を持ち込まない。「ポリゴン」「区域」のようにアプリ画面に出る語はそのまま使ってよいが、
  「リポジトリ」「同期スコープ」「LinkSelf」等の内部用語は書かない
- 画面の要素は**画面に表示されている文言そのまま**をかぎ括弧で引用する（「はじめる」を押します）
- 「何ができるか」より「**どういうときに何をするか**」を先に書く。機能の列挙ではなく手順にする
- ロールによる差は節を分けず、その場で一言添える（「編集メンバー以上が使います」）
- 断定できないことは書かない。sources を読んでも分からなければ、その項目は飛ばして最後に報告する

書式は `docs/wants/12_操作マニュアル.md`「本文中の特殊記法」に従う。

| 記法 | 用途 |
|---|---|
| `{{shot:<id>}}` 行頭単独、`\|` の後にキャプション | スクリーンショット。未撮影でも先に書いてよい |
| `{{topic:<id>}}` | 他マニュアルページへの相互リンク。表示名は自動 |
| `{{route:/map}}` | アプリのルート表記。実在しないと検査でエラーになる |

Markdown は意図的にサブセット。`#` 見出しと入れ子リストは使えない（`##` から始める）。
解釈できない書き方は黙って崩れず**生成時に例外**になるので、`npm run manual:build` で確かめる。

書き上げたら frontmatter の `status` を `published` にする。

### 手順 3: sources が実態と合っているか見直す

本文を書く過程で「この画面の説明にはこのファイルも要る」と分かることが多い。
参照したのに `sources` に無いファイルがあれば**追加する**。ここが漏れると、
そのファイルを直したときに陳腐化フラグが立たなくなり、仕組み全体が静かに効かなくなる。

逆に、もう参照していないファイルは `sources` から外す（無関係な変更で毎回 stale になるのを防ぐ）。

## スクリーンショット

本文が固まってから撮る。撮影の仕組みが未整備の間は、未撮影のまま `{{shot:}}` を残してよい
（本文は壊れず、プレースホルダが表示され、`manual:check` が警告として残す）。

## 仕上げ

```bash
cd pwa
npm run manual:build   # 記法エラーがないか（失敗したら本文を直す）
npm run manual:seal    # digest を現状に固定して stale を解消
npm run manual:check   # 残った警告を確認
npm test               # 生成物が型として通ることの確認を兼ねる
```

`manual:seal` は**本文を実際に見直した後にだけ**実行する。見直さずに seal すると、
古い本文に「最新である」という印をつけてしまい、陳腐化検知が機能しなくなる。ここがこの仕組みの唯一の弱点。

新しいマニュアルページを追加した場合は `docs/CODEMAP.md` の「12 操作マニュアル」節も見直す
（本文 md 個別は載せない。仕組み側のファイル構成が変わったときだけ直す）。

## コミット

- 本文（`docs/manual/`）・生成物（`pwa/src/manual/generated/`）・スクリーンショットを同一コミットにまとめる
- 実装変更に伴う更新なら、**その実装と同じコミットに含める**のが望ましい（分けると再び stale になる）
- コミットメッセージには「どのページを、なぜ直したか」を書く

## 報告すること

- 更新したページと、`published` にしたページ
- sources を追加・削除したページ（仕組みの効き方が変わるため）
- **sources を読んでも断定できず書けなかった項目**（これが最も重要な報告。推測で埋めない）
- 残った警告の件数

## やらないこと

- sources を読まずに書く（記憶・CODEMAP の説明・過去の会話だけで書かない）
- 本文を見直さずに `manual:seal` する
- 開発者向けの説明（内部構造・データ同期の仕組み・設計意図）をマニュアルに書く
- 中間ドキュメントの生成（CLAUDE.md 開発方針）
