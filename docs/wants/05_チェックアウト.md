# チェックアウト

## チェックアウトデータ

- チェックアウトデータ＝1つの区域の貸し出し
  - チェックアウトデータが区域データを参照する
  - チェックアウトは1つの区域のチェックアウト開始から返却（または完了）までの1つのデータが紐づく
  - 担当者は1名（編集メンバーが任命する／持ち出しのときは取得者本人）
- 「訪問活動」「訪問活動チーム」という上位概念は持たない
  - チェックアウトと返却の組をもって1回の活動を表現する
  - 同一区域を複数人で巡回する運用は、各メンバーが個別に訪問記録を作成することで表現する（チェックアウトは1つのまま）

## 区域の貸し出し（チェックアウト）モデル

- チェックアウトには2つの経路がある
  - **貸し出し**（編集メンバー主体）: 編集メンバーが活動メンバーに区域を貸し出す
    - 区域の貸し出しは排他的（同一区域に対してアクティブなチェックアウトは最大1つ）
    - 編集メンバー以上が **自分自身に貸し出す** ことも可能（`OwnerID == LentByID`）。訪問記録画面で入力するためにチェックアウトを取得するケースで使う
  - **持ち出し**（活動メンバー主体）: 活動メンバーが「持ち出し可能」区域を自主的に取得する
- 区域の可用性
  - 編集メンバーが網羅予定の中で、スコープに対して区域の可用性を設定する
  - **スコープ**（対象範囲）
    - グループ全員（スコープNULL）: LinkSelfグループ内の全メンバーが対象
    - 特定のグループ: 指定したグループのメンバーのみが対象
  - スコープに対して以下を設定する
    - **貸し出し可能区域**: ある期間に使用する区域を区域単位で設定する
    - **持ち出し可能区域**: 貸し出し可能区域の中から、活動メンバーが自主的に取得できる区域を設定する
      - 持ち出し可能 ⊂ 貸し出し可能（持ち出し可能は貸し出し可能の部分集合）
      - 貸し出し可能だが持ち出し不可の区域は、編集メンバーからの貸し出しでのみチェックアウトされる
- 可用性制約のバイパス（上位互換）
  - **編集メンバー以上はスコープ／貸し出し可能設定／持ち出し可能設定の枠外の区域でもチェックアウトできる**
  - これは編集メンバーが網羅予定の策定者であることと、「上位互換」の原則による
  - サービス層の可用性バリデーションは活動メンバーの貸し出し／持ち出し操作にのみ適用する

## ステータス管理

- 開始前、活動中、完了済み
- 活動中に返却できる（未完了の状態で返却・回収）

## 返却と回収

- 返却（活動メンバー主体）
  - 活動メンバーは主体的・明示的に返却できる
  - 完了していなくても返却できる
  - 返却期限は設定しない（物理カードではないため）
- 回収（編集メンバー主体）
  - 編集メンバーは返却されていない区域を強制回収できる
  - 滞留時は編集メンバーが強制回収で対応する
- 再貸し出し
  - 返却・回収後は他のメンバーへ再貸し出しができる
  - 再貸し出し時は貸し出し操作を行った編集メンバーが新しい担当者を任命する

## 担当者

- チェックアウトごとに1名の担当者を持つ
  - 貸し出し時：編集メンバーが任命する（自分自身を担当者にすることも可）
  - 持ち出し時：取得した活動メンバー本人が担当者となる
- 担当者は便宜的な存在であり、編集メンバーが任意のメンバーへ任命変更できる
- 担当者として記録された人物と、実際に訪問記録を作成する人物は一致しなくてもよい（同行者など）
  - 訪問記録は `VisitRecord.UserID` で記録者を保持する
- **編集メンバーから活動メンバーへの担当者移譲**
  - 編集メンバーが「自分でチェックアウトして記録 → 活動メンバーへ継続を任せる」というワークフローでは、新規にチェックアウトを作り直さず、既存チェックアウトの担当者を `ReassignOwner` で活動メンバーへ付け替える
  - これによりチェックアウト単位での活動成果（訪問記録の集計）が分断されず、編集メンバーが作成した訪問記録も継続活動の一部として一貫的に扱える
  - 既存の招待（区域招待）も担当者変更で維持されるため、応援メンバーの作業も継続される

## 区域へのアクセス権

訪問記録画面における権限を **閲覧** と **入力** に分けて定義する。

### 閲覧権限

- **編集メンバー以上**: 全区域の訪問記録画面を閲覧できる（チェックアウトの有無を問わない、上位互換）
- **活動メンバー**: 自分が「入力権限」を持つ区域のみ閲覧できる
  - （閲覧と入力を別レイヤーで管理する必要は薄いため、活動メンバーは入力可能区域＝閲覧可能区域として扱う）

### 入力権限

訪問記録を入力（作成・編集）するには、**当該区域に対して自分が関与する `active` なチェックアウトが存在すること** が必須。`VisitRecord.CheckoutID` は **NOT NULL** とし、いかなる訪問記録もチェックアウト1件と必ず紐づく。

入力権限を持つのは以下のいずれか：

- 当該チェックアウトの **担当者**（活動メンバー／編集メンバー以上のいずれでも可）
- 当該チェックアウトの **有効な招待を受けた被招待者**（次節「区域招待」）

ロール別に整理すると：

- **編集メンバー以上**
  - 閲覧は常時可能
  - 入力したい場合は **自分でチェックアウトする** か、誰かの招待を受ける必要がある
  - 当該区域にすでに他者の `active` チェックアウトがある場合は二重チェックアウト不可（排他的貸出）。招待を受けるか、必要なら強制回収して自分のチェックアウトに切り替える
- **活動メンバー**
  - 閲覧・入力ともに「自分が担当者」または「有効な招待を保有」のいずれかを満たす区域のみ可能

### アクセスモード（読み取り／編集の二層モデル）

訪問記録画面における編集可否は **区域レベル** と **場所レベル** の2層で管理する。両者の組み合わせにより、各場所の **有効モード（effective mode）** が決まる。

#### 区域レベル（親レイヤー）

- 当該訪問記録画面を開いたユーザがその区域に対して入力権限（active チェックアウトに自分が関与しているか）を持つかで決まる
- 状態
  - **editable**: 自分が担当者、または有効な招待を保有
  - **read-only**: 上記いずれも満たさない（編集メンバー以上はこの状態でも閲覧可、活動メンバーは到達しない）
- 区域レベル read-only のときの挙動
  - 画面上部に **「この区域をチェックアウトして記録する」誘導 CTA** を配置
    - active チェックアウトなし → ボタン押下で即時チェックアウト（自分が担当者となる `lending` 種別）
    - 他者の active チェックアウトあり → 「招待を依頼」または「強制回収して自分でチェックアウト」の2選択肢を提示（強制回収は確認ダイアログ＋監査ログ記録）
  - チェックアウト確立後は区域レベルが editable に切り替わる

#### 場所レベル（子レイヤー）

- 場所単位で個別の編集可否を管理する。特殊な状態（後述の用途）に対応するための拡張ポイント
- 状態
  - **editable**: 通常状態
  - **read-only**: 場所単独で読み取り専用扱い
- 想定用途（順次具体化）
  - 招待期間切れ後の被招待者が、活動中に観察した特定の場所だけを後から見直したい・個人記録を追加したい（`09_継続的検討事項.md` の「招待された活動メンバーの再訪問ニーズ」とも連動）
  - 訪問拒否宅・特殊扱い場所の編集制限
  - 期間終了後の参照専用化
- 現フェーズでは **モデルとデータ構造として用意し、UI からの read-only 切替操作は未実装** とする。判定 API は実装する（既定値は editable）

#### 親子関係（有効モードの決定ルール）

| 区域レベル | 場所レベル | 有効モード |
|---|---|---|
| editable | editable | **editable** |
| editable | read-only | read-only |
| read-only | editable | read-only（区域が支配） |
| read-only | read-only | read-only |

- **区域レベルの read-only は場所レベルを上書きする**（親が支配的）
- 場所レベルの editable は、区域レベルが editable のときだけ意味を持つ
- 訪問記録の保存・編集は有効モードが editable の場所でのみ可能

## 区域招待

担当者ではない活動メンバーを、特定のチェックアウト区域に時間制限付きで参加させる仕組み。同行や応援目的で他の活動メンバーが訪問記録を作れるようにする。

- 招待者
  - 編集メンバー以上、または当該チェックアウトの担当者である活動メンバー
- 被招待者
  - 同一 LinkSelf グループ内の活動メンバー（担当者本人を除く）
- 招待発行可能なチェックアウト状態
  - **`active`（活動中）のみ**
  - `pending`（開始前）／`returned`（返却済み）／`complete`（完了済み）では招待発行不可。UI 上も招待ボタンは活動中のチェックアウト詳細でのみ活性化する
  - 事前準備のニーズは、貸し出し時に最初から担当者として任命するか、別途活動が始まったタイミングで招待を発行する運用で対応する
- 招待の単位
  - 1つの招待は「1つのチェックアウト × 1人の被招待者 × 有効期限」を表す
  - 同じチェックアウトに対して複数の招待を並行発行できる
  - **同時発行数の上限は設けない**（有効期限による自然失効でデータ量は構造的に膨張しない／運用判断に委ねる）
  - **同一被招待者への重複招待は「期限延長（上書き）」として扱う**
    - 同一チェックアウト × 同一被招待者の有効な招待がすでに存在する状態で再発行されたら、既存レコードの `ExpiresAt` を新しい値で上書きし、新規レコードは作らない
    - 旧期限から短くする上書きも許容する（招待者の意図的な短縮）
    - 旧期限の値が必要な場合は監査ログ（`07_通知と申請.md`）に記録する
    - 上書き時も Q5 の方針に従い、被招待者へ新規通知を1通送る（被招待者は「期限が延長／変更された」事実を把握できる）
- 有効期限
  - **デフォルトは発行時刻から 24 時間**
  - UI 上で個別に変更可能だが、通常は変更不要として既定値の運用を推奨する
  - 期限切れ後は自動的にアクセス権が失効する（被招待者の訪問記録画面から当該区域が外れる）
- 失効・取り消し
  - チェックアウトが返却・**強制回収**されたタイミングで、紐づく未失効の招待もすべて失効する
  - **再貸し出し時の引き継ぎは行わない**：強制回収後に同じ区域が別の活動メンバーへ再貸し出しされた場合でも、旧チェックアウトに紐づいていた招待は新チェックアウトへ自動引き継ぎされない。新チェックアウトで被招待者が必要なら、新担当者または編集メンバーが改めて招待を発行する
  - 有効期限内であっても、以下のいずれかが招待を取り消せる
    - 招待者本人
    - 当該チェックアウトの**現**担当者（担当者変更後はその時点の担当者）
    - 編集メンバー以上
- 担当者変更時の招待の扱い
  - チェックアウトの担当者を別メンバーに変更した場合でも、既存の未失効招待はそのまま**維持**される
    - 招待は被招待者ごとに付与された区域アクセス権であり、担当者という別レイヤーの状態変更で剥奪されない
    - 現場で活動中の被招待者が担当者交代によって突然弾かれることを防ぐ
  - `InviterID`（招待発行者）は監査ログ上の履歴として保持し、担当者変更で付け替えない
  - 招待の取消責務は前項のとおり「現担当者にも委譲」されるため、旧担当者が離れた後も取消経路は維持される
- 招待中の被招待者の権限
  - 担当者と同等の訪問記録入力権限を持つ（記録者は `VisitRecord.UserID` で各自として記録される）
  - 担当者の変更・チェックアウト返却操作は行えない

### 招待 UI

- チェックアウト詳細画面に「招待」セクションを設ける（active チェックアウトでのみ表示）
- 招待発行ダイアログ
  - 被招待者選択
    - **既定の候補リスト**: 同一 LinkSelf グループ内の活動メンバー全員（担当者本人を除く）
    - **OrgGroup フィルタ**: ドロップダウンで OrgGroup を選択し、当該グループ所属の活動メンバーに絞り込み（既定は「全グループ」）
    - **インクリメンタルサーチ**: テキスト入力で氏名等を逐次マッチして候補を狭める
    - 上記フィルタとインクリメンタルサーチは併用可能。複数選択可
  - 有効期限：既定 24 時間。プルダウン等で変更可能（例: 6h / 12h / 24h / 48h、または任意指定）
  - 発行ボタンで確定。被招待者へ通知が飛ぶ
- 既発行の招待一覧
  - 被招待者名、残り時間、状態（有効／期限切れ／取り消し済み）を表示
  - 取消可能な操作者は「失効・取り消し」節で定義済み（招待者本人／現担当者／編集メンバー以上）
