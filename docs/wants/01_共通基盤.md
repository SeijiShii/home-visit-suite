# 共通基盤

## データ構造方針

- 全てのデータは木構造とする
- データの競合解決（同期・マージ）はLinkSelfのカバー範囲とする

## 用語定義

- 本仕様における「区域」は運用上の最小単位（枝番レベル）を指す
  - 正確には区域とは枝番の集合だが、メンバーが主に扱うのは枝番レベルであるため「区域」と呼称する
- 枝番の集合としての上位概念は「区域親番」と呼ぶ

## アプリの関係

- **単一 PWA + ロール別 UI**（2026-07-07 全面 PWA 化決定）。管理・編集向け機能と活動メンバー向け機能は同一アプリ内で権限ゲートにより出し分ける
- 管理・編集ロールの UI は活動ロールの UI の上位互換である（上位ロールは下位を包含）
  - 管理・編集ロールは訪問記録の閲覧・編集も可能
  - 管理・編集ロールの地図は編集可能、活動ロールの地図は閲覧・訪問記録用
  - 活動メンバーは管理・編集系画面にアクセスできない（権限ゲート）

## 実行環境

- **単一 PWA として全プラットフォームのブラウザで動作させる**（2026-07-07 決定。動機: ストア審査を経ずに配布・更新するため）
  - デスクトップ: Windows / Mac / Linux のモダンブラウザ
  - モバイル: iOS Safari / Android Chrome（ホーム画面追加でアプリとして利用）
- 旧構成（管理: Wails デスクトップアプリ / 活動: モバイルネイティブ）は廃止。Wails 版は新規開発凍結・段階的廃止（React 資産は PWA へ移植）
- ブラウザ実行の前提制約
  - LinkSelf はブラウザ向け TypeScript 実装（Go 実装とワイヤ互換の第二実装）を使用する（`11_LinkSelf拡張要望.md`）
  - ブラウザピアは外部からの着信を受けられないため、常時稼働ノード（リレー／ブートストラップ／メールボックス）が必要
  - バックグラウンド実行はゼロ（タブ／PWA を閉じると完全停止）。前景起動時に高速差分同期するライフサイクルを前提とする
  - オフライン対応は Service Worker（GSI タイルキャッシュ等）+ OPFS 永続化で設計する

- **デプロイ**: `pwa/scripts/deploy-oci.sh`（本番ビルド → rsync → 完了報告）。本番値は `pwa/.env.production.local`（gitignore 対象）に固定する。Vite の production モードで `.env.local` の開発値を上書きする（優先順位: `.env.production.local` > `.env.local`）。`VITE_PAIRING_BASE_URL` は空＝実行時オリジン（本番で正しい）。スクリプトはこのファイルが無いとエラー終了する（開発値の焼き込み防止）

### ストレージ（LinkSelf MyDB / SQLite3）

- LinkSelf の `MyDB` を経由して SQLite3 にデータを永続化する
  - SQL（`Exec/Query/QueryRow/Migrate`）と KV（`Put/Get/Delete/List`）の両 API を持ち、書き込みは透過的に同期される
  - DB ファイル配置は LinkSelf 側で `<dataroot>/<DID>/suites/<SuiteID>/data.db` に自動配置（`Config.SuiteID = "jp.home-visit-suite"`）
- PWA では LinkSelf TS 実装が sqlite-wasm + OPFS 上に同等の `MyDB` API を提供する（旧 Wails 版は go-sqlite3 で単一プロセスアクセス前提）
  - 複数タブからの同時アクセスは単一アクセサに直列化する（Web Locks / SharedWorker 等、方式は LinkSelf TS 実装側で決定）
- スキーマは起動時に `MyDB.Migrate` で適用する
- **暫定ブリッジ（LinkSelf TS 実装完成まで）**: 現状は InMemory リポジトリ + localStorage 永続で動作させる。runtime（`createInMemoryServices({ persist: true })`）では全ドメインデータ（領域・区域・場所・チェックアウト・網羅・通知）と個人設定（言語等）を localStorage に write-through 永続化し、再読み込みでも保持する。テストは `persist` 省略でインメモリのまま。dev のロール切替（3 種の疑似ユーザーを選べる identity 切替 UI）は**既定で無効**で、環境変数 `VITE_DEV_IDENTITY` を明示的に有効化したときのみ疑似ユーザーを毎起動シードする（通常の `npm run dev` は実 identity＝オンボーディングフローで動作）。**自分の identity（`hvs.identity`）だけは localStorage に永続**し、起動時に自己ユーザーを UserRepository へ復元する（「自分の ID の作成と保管」参照）。LinkSelf 導入時に本リポジトリ層を差し替える（秘密鍵等の平文保存も暗号化ストレージへ移行）
- **グループ毎のローカル DB 分離（2026-07-15）**: ローカルの永続データは**グループ（networkId）毎に名前空間を分離**し、グループ切替で相互に汚染せず保全する
  - ScopeNetwork 系（ドメインデータ・共有レコード・catch-up 高水位・membership epoch・グループ名・既知メンバー）は networkId 毎の名前空間（OPFS DB ファイル / localStorage プレフィクス）に保存する
    - **OPFS の制約**: SAHPool VFS はプールディレクトリ単位で Access Handle を排他取得するため、複数 DB（個人 DB + グループ DB）を同時に開くには **DB ファイル毎に専用プール**（link-self `SqliteWasmOptions.vfsPool`）を使う。個人 DB（`hvs-personal.db`）だけは既存データ互換のため既定プールに残す（2026-07-15）
  - ScopeDevice 系（デバイス登録簿・アプリ設定）はグループ非依存で端末（ユーザー）に 1 つ。ただし個人メモ・個人タグ割当などグループ実体（場所・区域）に紐づく個人データはグループ名前空間側に置く
  - **切替 = アクティブグループポインタの変更 + アプリ再読み込み**（LinkSelf クライアントと同期スコープをアクティブグループで配線し直す）
  - 既存の単一グループ前提のデータ（無印 `hvs:*` / `hvs.networkId` 等）は初回起動時に一度だけアクティブグループの名前空間へ移行する

### 同期スコープ（SyncScope）

各テーブルは `SetSyncScope` で同期範囲を指定する。

| スコープ | 対象テーブル | 同期範囲 |
|---------|-------------|---------|
| `ScopeNetwork` | regions, parent_areas, areas, places, map_*, users, member_tags, available_periods, available_period_tags, available_period_parent_areas, checkouts, checkout_invitations, visit_records, visit_record_edits, coverages, requests, invitations, notifications, audit_log | LinkSelf ネットワーク内全メンバー |
| `ScopeDevice` | personal_notes, personal_tags, personal_tag_assignments, my_settings, **devices** | 同一ユーザーの端末間のみ |
| `ScopeLocal`（同期しない） | 端末固有で共有すべきでない個別設定 | その端末のみ（非同期） |

- **デバイス登録簿（`devices`）は `ScopeDevice`（同一ユーザーの端末間で同期）**。端末の追加・改名・削除が自分の全端末へ反映され、廃棄・誤登録した端末を別端末から一覧・削除できる（`個人デバイスの管理`）。暫定 localStorage 実装は M5 でこの `devices` テーブルへ移行する
- **同期タイミング**: 書き込みは MyDB 経由で透過的に伝播する。前景かつオンライン中は変更時にほぼ即時、相手がオフラインならメールボックス（store-and-forward）に預け、その端末の次回前景起動の差分同期で受信する（`実行環境`「前景起動→高速差分同期→graceful stop」）。したがって**デバイス登録・削除や設定変更も“変更時”に同期対象**になる（起動時のみの一括同期ではない）
- **端末ローカル（`ScopeLocal`・非同期）**: 端末固有で共有すべきでない個別設定は同期しない。同期の要否は設定項目ごとに判断する（デバイス登録簿は同期必須、端末固有の UI 設定等は端末ローカルでよい）
- App 内のメンバーグループ（旧 `org_groups`）概念は廃止済み。ロール（管理者・編集メンバー・活動メンバー）とメンバータグでメンバー分類は表現する
- Topic ベースのサブスクリプションでトラフィック最適化（活動メンバーは自分が関与する領域・区域の topic のみ購読）

#### 実装状況（2026-07-14: Phase C 完了・users 系を移行）

- link-self の **Phase C（MyDB × groupshare = ScopeNetwork の実効化）が完了**し、`setSyncScope(table, "network", {networkId})` でテーブル単位のメンバー間同期が動く（チャネル `mydb:<networkId>:<table>`・LWW・削除は墓石保持・接続時 catch-up `group_sync_req`）
- **移行済みテーブル: `users` / `member_tags`**（`LinkSelfUserRepository` = MyDB SQL。OPFS 永続 + ScopeNetwork）。参加受理・任免・改名・タグが全メンバーへ伝播し、受信時は window イベント（`hvs:shared-applied`）で開いている画面が再読込する。旧 localStorage 実装からは SQL 側が空のとき一度だけ自動移行する
- **配線の要点**: 共有レコードと membership epoch は localStorage 永続（`hvs.sharedRecords` / `hvs.membershipEpochs`。リロードで catch-up 高水位・LWW 判定材料・epoch を失わないため）。ScopeNetwork 昇格の `includeExisting`（既存データ一括配送）は**初回のみ**（`hvs.scopedTables` フラグ。毎起動で行うと新タイムスタンプ再配送が他端末の新しい状態を上書きし得るため）
- **伝播の成立条件（現状の制約）**: メンバー同士が libp2p 接続中であること。presence（端末発見）未実装のため、**参加時に招待へ載っていた管理者の到達アドレスを保存し（`hvs.knownMembers`）、次回起動の FastStart で管理者へ再ダイヤルするハブ型トポロジ**で catch-up を成立させる。双方が同時にオンラインにならないメンバー間の中継（グループデータのメールボックス預かり）と presence は今後の課題
- 残りの ScopeNetwork テーブル（regions/areas/places/map_*/checkouts/visit_records 等）は同じ器（MyDB SQL リポジトリ + setSyncScope）へ順次移行する

### 自分の ID（identity）の作成と保管

- ユーザーの識別子は LinkSelf の DID（`did:key` 形式）とする。LinkSelf TS 実装 `@linkself/core` の `generateIdentity()` が Ed25519 鍵対と DID を生成する（Go 実装とバイト互換: `0xed` + 32byte 公開鍵を base58btc + `z` 接頭辞）
- **初回オンボーディング**: ローカルに identity が無い初回起動時はオンボーディング画面を出す。表示名を入力して「はじめる」で新しい identity を生成し、自分の User レコードを作成して入室する。以後の起動は保存済み identity をロードして直接入室する
- ここで生成・保管する identity は **ユーザー identity（アカウント）**。端末ごとの**デバイス identity（デバイス鍵/DID）**は別途各端末で自動生成する（`端末ペアリング` の 2層モデル）
- **秘密鍵の保管（暫定）**: 現状は以下を `localStorage` に保存する。LinkSelf 本統合（M5）時に WebCrypto 非抽出鍵 + OPFS の安全ストレージへ移行する（API キー等と同様の秘匿情報として扱う）
  - `hvs.identity`: ユーザー identity（`did` / 秘密鍵シード / 表示名 / ロール）
  - `hvs.deviceKeySeed`: この端末のデバイス鍵シード（32byte、決定的復元で peerId 固定）
  - `hvs.deviceRoster`: ユーザー鍵署名のデバイスロスター（`userDID→[deviceDID]`、marshal 済み）
- 起動時、保存済み identity があれば（毎起動シードの）UserRepository へ自分の User を upsert して自己ユーザーを復元する
- 自分の DID は招待・通知の宛先として使う（Go 版 `Client.NodeInfo` 相当は TS では `client.did`）
- **表示名の変更（2026-07-14）**: 自分の表示名は設定画面のプロフィールセクションでいつでも変更できる。`hvs.identity` の表示名と自分の User レコードの両方を更新する（タグ・参加日時は保持）。**他メンバー端末への伝播は users テーブルの ScopeNetwork 同期に乗る**（同日 Phase C 完了 + users 移行済み。伝播条件は「同期スコープ」の実装状況を参照）。起動時の自己ユーザー復元は**リポジトリ側のレコードを正**とし、`hvs.identity` の古いキャッシュで同期済みの表示名・ロールを上書きしない
  - **同名の禁止**: グループ内に同じ表示名のメンバーが既に存在する場合、変更はエラーとする（管理者によるメンバー編集での改名も同様）。サーバーレス P2P のため検証は**各端末のローカルなメンバー表**に対するもの（メンバー表を持つ管理者端末が実質の正）
- **サイドバーの自己情報表示（2026-07-14）**: アプリ共通レイアウトのサイドバー下部に、自分の表示名と現在のロールバッジを常時表示する（自分が誰として・どの権限で操作しているかを見失わないため。開発モードのアクター切替時は切替先を反映する）

### 端末ペアリング（同一 ID の別端末追加）

- 同一ユーザーの別端末（PC で作成した ID にスマホを追加する等）は、LinkSelf のペアリング（`@linkself/core` の `createToken` / `PairingSession` / `complete` / `exportPrivateKey` / `importIdentity`）で追加する。
- **identity モデルは 2層（ユーザー鍵＋デバイス鍵）**（`data-sync-decisions` P3 / link-self `roster.ts` 実装済み）:
  - **ユーザー鍵 / ユーザー DID**: アカウントの識別。ネットワークに公開され（`client.did`）、全端末で共有する。ペアリングで新端末へ転送する（フルコピー）
  - **デバイス鍵 / デバイス DID**: 端末固有。各端末が自分で生成し、**libp2p の transport 鍵（= peerId ≡ デバイス DID）**として使う。ネットワークには公開しない
  - **デバイスロスター**: `ユーザー DID → [デバイス DID]` を**ユーザー鍵で署名**したもの（`devices` 登録簿の暗号形）。端末間 devicesync の信頼の起点＝「相手のデバイス DID が自ユーザーのロスターに載っているか」で兄弟端末を判定する（Noise が transport 鍵を、ロスターがユーザー帰属を証明するので、端末間の追加 auth は不要）
  - ペアリングでは**ユーザー鍵のみを転送**する。新端末は自分のデバイス DID を生成してロスターに自己登録し、接続時のロスター交換で兄弟端末へ収束させる
- **チャネル（暫定・URL 方式）**: ネットワーク越しの鍵配送は LinkSelf 側が未実装のため、当面はオフラインで成立する **URL を載せた QR** を用いる。既存端末（例: PC）は設定画面「デバイス」でペアリング用トークン（`{secret, expiresAt}`、TTL 数分）と鍵素材を含む **アプリの URL（`/pair`）** を QR として表示する
  - **アプリ内カメラでのスキャンは行わない**。新端末（例: スマホ）は OS のカメラアプリで QR を撮影する、または URL をブラウザに直接入力することで、アプリ（`/pair`）にリダイレクトされ、同一 identity を復元して個人デバイス登録が完了する
  - **鍵素材は URL フラグメント（`#/pair?d=...`）に載せる**。フラグメントはサーバーへ送信されないため秘匿レベルは QR/localStorage と同等を保つ。取り込み後はフラグメントを履歴から除去する（`history.replaceState`）
  - URL のベースは既定で実行時オリジン（`window.location.origin + BASE_URL`）を用いる（本番は自動で正しい）。`VITE_PAIRING_BASE_URL` で正規の公開 URL に上書きできる（localhost からスキャンできない開発時、プロキシ/独自ドメイン背後など）
  - カメラ・リダイレクトが使えない場合の手入力（URL/コード貼付）フォールバックをオンボーディングに用意する
- **冪等性と DID 照合（2026-07-15 改訂）**: `/pair` URL の取り込みは、ローカル ID の有無と QR の DID の照合で分岐する
  - **未登録端末**: QR の鍵素材から同一 identity を復元して登録する。**ID の事前作成は不要**（グループ招待と同様、この画面だけで紐づけまで一貫して完了する。オンボーディングを経由させない）
  - **登録済み・同一 DID**: 追加登録せず登録済み ID でそのままアプリを開く（冪等・payload は無視）
  - **登録済み・別 DID**: 無条件でスルーしない。「この端末は別の ID で使用中」であることと QR 側の ID を提示し、**ユーザーの明示確認を経て QR の ID へ切り替えて紐づけ直せる**。切替時は旧 ID のローカルなグループ状態（所属ネットワーク ID・非同期参加の成立待ち/持ち越し結果・グループ名・メンバー表の旧自己レコード）を破棄する（誤ってオンボーディングで独立 ID を作ってしまった端末の救済経路。旧 ID 時代に同期済みのドメインデータの完全消去までは行わない＝暫定制約）
  - **失敗時（期限切れ・URL 破損等）**: オンボーディング（新規 ID 作成）へは誘導しない。**既存端末で QR を再発行して再スキャンする**案内を出す（新規作成へ流れると意図せず独立グループが成立する事故になるため）。ID 未作成端末には「紐づけをやめて新しい ID を作成する（既存 ID とは別のグループになる）」ことを明示した退避導線のみ残す
  - **成立時**: アプリを再読み込みし、取り込んだ実 identity で LinkSelf を配線し直す（設定画面のプロフィール・デバイス一覧が紐づけ後の ID を反映する）
- **個人デバイスの管理（設定画面）**: 設定画面「デバイス」で、自分の ID に紐づくデバイスを管理する
  - 各デバイスは**デバイス DID**（端末固有の Ed25519 鍵・libp2p peerId）とラベルを持ち、`userId`（自分のユーザー DID）に紐づく（`ScopeDevice` のデバイス登録簿＝ユーザー鍵署名のデバイスロスター）
  - ラベル編集と、**当該デバイス以外の削除**（誤登録・端末廃棄時）ができる
  - **当該デバイス自身は削除できない**（設定画面から自分の登録を解除する導線は設けない。何が起きるか不明瞭で誤操作の温床になるため）。不要な端末は、残す別端末の一覧から削除する
  - **削除の意味（2026-07-15 確定: ロスター失効＋対象端末の全初期化）**:
    - 残す端末の一覧から、当該以外の任意の端末（ローカル行・ロスター由来行とも）を削除できる（ロスター行の削除はネットワーク配線時のみ＝スタンドアロンでは失効を書けないためボタンを出さない）
    - **失効は tombstone（明示的な失効記録）**: 削除操作は対象デバイスをロスターの掲載（devices）から除外すると同時に **失効記録（removed）へ追加**し、rev+1 で再署名する。「掲載に無い」だけでは削除と解釈しない——ペアリング直後は発行側がまだ新端末を学んでおらず「掲載に無い」が正当に発生するため、不在をワイプの根拠にすると新端末が誤って初期化される（独立レビュー検出）。merge は tombstone を **union（再追加拒否・高 rev 側が失効を知らなくても再適用）**するため、失効は復活しない恒久記録になる（ワイプされた端末は新しいデバイス鍵を作るので、同じ DID が正当に戻ることはない）
    - 削除操作は失効後ロスターを残る兄弟端末へ即時 announce（rev merge で伝播）するとともに、**対象端末宛にも直接送る**（オンラインなら即時。オフラインなら削除操作をした端末が送信キュー（メモリ）に保持し、対象端末がその端末へ接続してきたときに配送＝best-effort。残る兄弟端末いずれかとの接続時の announce でも届くため、実質「対象端末が次にいずれかの兄弟と出会ったとき」に成立する。リレー常駐の恒久キュー＝メールボックス経由は将来課題）
    - **対象端末は「自分の tombstone を含む、自ユーザー鍵署名のロスター」を受理したら全初期化する**: identity（ユーザー鍵）・全グループの DB・localStorage をすべて消しオンボーディングへ戻る（部分ワイプや「データを残して同期だけ停止」の選択肢は設けない＝切り離された端末へのグループデータ残置を正規状態にしない。2026-07-15 ユーザー決定）。受理したままワイプ未完で再起動した場合も起動時チェックで初期化する。オンボーディングには「別の端末からこの端末の登録が削除されました」の通知を表示する
    - **「他 ID の端末としてグループに残す」案は却下**（2026-07-15 ユーザー決定）: 個人 ID から切り離された端末はグループ内で通用する ID を持たないため、独立した人格としてグループに残すことはしない。改めて参加させたい場合は通常のグループ招待（新規メンバー）を使う
    - 悪用ガード: 失効はユーザー鍵署名のロスターでのみ成立する（署名検証は mergeSiblingRoster）。同一ユーザーの端末＝ユーザー鍵保持者だけが発行でき、グループの他メンバー・管理者には発行できない
    - 構造的制約: 以後一度も接続しない端末には初期化指示が届かない（サーバーレス P2P にリモート強制消去は存在しない）。その場合もロスターから外れているため同期・配送の対象にはならない。OPFS ファイルの物理削除は best-effort（SAHPool 制約。スロット参照が消えるため実害はない）
    - 復帰: 初期化後にペアリング URL を渡せば**新しいデバイス DID として**再登録（再同期）できる
  - **ラベルの同期（2026-07-15 実装）**: ラベルの SoT は**デバイスロスター**（各エントリが `deviceDID + label` を持つ）。ラベル変更はロスターを再署名（rev+1）して永続し、接続中の兄弟端末へ即時 announce する。受信側は rev 比較で新しいロスターを採用し、デバイス一覧へ再読み込みなしで反映する。自端末・兄弟端末のどの行もどの端末からでも改名できる
- **自己端末間のローカルデータ同期（2026-07-15 要件化）**: 同一ユーザーの端末間で、ローカルデータ（ScopeDevice 系＋所属グループの ScopeNetwork 系）は同期して収束させる。汎用の presence（端末発見）を待たず、以下で「2 端末が出会う」ことを成立させる:
  - **兄弟端末への直接ダイヤル**: リレーは固定（`VITE_LINKSELF_RELAYS`）のため、相手のデバイス DID（= peerId）が分かればリレー circuit アドレス（`<relay>/p2p-circuit/p2p/<deviceDID>`）を構成してダイヤルできる。ロスターに載る兄弟デバイス DID を FastStart のダイヤル対象に加える
  - **ペアリング payload の拡張（2026-07-15 改訂: 鍵＋最小限のポインタのみ）**: QR には**鍵素材（seed）と最小限のポインタだけ**を載せる——発行側端末の**デバイス DID（1 個）**と**所属グループ一覧（networkId + 表示名のみ）**。**ロスター本体・ネットワーク実体（メンバー・ロール表）は載せない**（同梱すると QR がグループ人数に比例して高密度化し実機カメラで読めない。実測で発覚）
    - 新端末は紐づけ直後に (a) 発行側デバイス DID を「ロスター追加待ち」に控え、次回起動時に自分のユーザー鍵で追加署名する（鍵は seed で受領済み＝同じ信頼水準） (b) 所属グループの器（グループ名前空間）を作り、ネットワーク実体は**自分のメンバーシップのみで自己合成**する (c) 発行側端末へダイヤルし catch-up で収束する
    - **兄弟端末レプリケーション（link-self 2026-07-15 実装）**: 同一アカウントの端末は従来「自分除外」でグループデータ配送から漏れていた。ロスター掲載の兄弟端末を groupshare 配送・catch-up 要求・アカウント解決の対象に加え、兄弟からの group_sync_req には membership snapshot を保存済み epoch で応答する（最小実体の端末は epoch を新造しないため、本物の実体を上書きする逆流は LWW で構造的に防がれる）
  - **ロスターの収束（2026-07-15 改訂: rev + tombstone 付き）**: ロスターは**単調増加のリビジョン（rev）**と**失効記録（tombstone）**を持ち、ユーザー鍵で署名する。接続時の auth 成功で announce し合い、自アカウントのロスターは署名検証のうえ **rev が高い方を全面採用**（ラベル変更・失効が伝播する。ただし手元の tombstone を欠く場合は再適用して rev+1）、**同 rev 以下は未知かつ非失効のデバイス DID のみ union して rev+1 で再署名**（ペアリング直後の新端末=低 rev から発行側が新デバイスを学ぶ経路。tombstone も union し、失効済み DID は復活させない）する（link-self TS `roster.ts` / `client.ts`）。これにより発行側端末も新端末を兄弟と認識し、双方向 devicesync とデバイス一覧への反映が成立する
    - **同 rev 競合のタイブレーク**: 同 rev・同一デバイス集合でラベルだけ食い違う並行編集は、正規形バイト列の辞書順で決定的に勝者を選び rev+1 で採用する（片方の編集は消える＝同時編集の LWW として許容。放置すると永久に発散するため）
    - **統合結果の再アナウンス**: merge で自ロスターが変わったら、接続中の兄弟端末へ統合結果を即時 announce する（相手の次回接続を待たない。内容一致なら merge が null になるため無限往復しない）
    - **旧 v1（rev 無し）ロスターの移行**: rev 導入前に永続されたロスターは load 時に掲載台数を下限とした rev で一度きり再署名する（rev 0 のまま残すと新規端末の低 rev に全面採用で負けて既存兄弟が脱落するため）
  - **デバイス一覧への反映**: 設定画面「デバイス」は自端末の登録簿に加えて**ロスター掲載の兄弟端末**を表示する。ラベルはロスターを SoT として全行表示・全行編集でき、削除（ロスター失効＋対象端末の全初期化＝上記「削除の意味」）も当該デバイス以外の全行で可能
  - **ロスター更新の即時 UI 反映（2026-07-15 追加）**: ロスターの統合・ラベル変更時は `hvs:roster-updated` イベントを発火し、開いている設定画面のデバイス一覧を**再読み込みなしで**更新する（ペアリング成立後に発行側で新端末が現れない・何度も再読み込みが要る問題の解消）
  - **兄弟端末への定期再ダイヤル（2026-07-15 追加）**: 既存の 60 秒ポーリング（メールボックス確認）に合わせ、**未接続のリレーと兄弟端末（ロスター掲載）へ再ダイヤル**する。片側だけ先に起動していて相手を知らない・一時切断後などに、再読み込みしなくても出会い直して catch-up が走るようにする。対象は peerId ≡ DID で接続済み判定が効く相手（リレー・兄弟端末）に限る（既知メンバー=アカウント DID を含めると接続済みでも毎回再認証され、auth 後フックが定期的に全員分走るため）
  - 接続後は link-self 実装済みのフローに乗る: auth 成功 → ロスター announce → group catch-up（`group_sync_req`）→ devicesync（ロスター掲載端末のみ対象・ユーザー鍵署名が信頼の起点。`roster-devicesync.e2e` で実証済み）
  - presence（相手の現在アドレス解決・オンライン検知）は将来の最適化であり、同期成立の前提としない。収束まではデータが端末毎に異なり得る旨を UI に明示する
- ネットワーク作成・メンバー招待・脱退は LinkSelf の `Network` API で管理する

  - 言語切替（ja / en）。従来サイドバーに置いていた切替は設定画面に統合する

## 言語・ローカライゼーション

- UI 言語は `ja` と `en` を最初から両方用意する
- 言語設定はユーザースコープ（LinkSelf 個人設定、キー `ui.locale`）で保存する

- 旧実装の `localStorage` locale キーがあれば初回起動時に LinkSelf へ移行する

## ツールチップ基盤（共通 UI）

- 画面右上に表示するツールチップ型のヘルプ基盤を共通で提供する
- i18n キー命名規則: `tips.<画面>.<動作>` (例: `tips.map.polygon.startDraw`)
  - 将来の他画面追加に備え、汎用的な基盤として設計する
- 振る舞い
  - 新しいメッセージは右上にスライドダウンで出現し、約 5 秒後にフェードアウト
  - 連続表示は 1.5 秒間隔のキューで順次投入
  - 同時表示は最大 5 件、超過時は最古から即時消去
  - 新しいメッセージは先頭に積まれ、既存は下へ押し下げる
  - 同一キーが既に表示中の場合は重複投入しない
  - 各メッセージに「このメッセージを表示しない」リンクがあり、クリックで該当キーを永続的に非表示化
- 非表示化したキーは LinkSelf 個人設定 (`ui.hiddenTipKeys`) に保存
- 設定画面の「ヘルプ表示をリセット」で一括解除可能
