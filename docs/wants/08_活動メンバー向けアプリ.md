# 活動メンバー向けアプリ

> 2026-07-07 全面 PWA 化決定により、本ドキュメントは**単一 PWA のうち活動メンバーロールが利用する機能**の仕様を扱う（独立したモバイルアプリではない）。

- 地図主体の UI
- 実装方針（2026-07-07 改訂）: **単一 PWA のロール別 UI の一部**として提供する
  - iOS / Android / デスクトップのブラウザで動作し、モバイルではホーム画面追加でアプリとして利用する（ストア審査を経ない配布・更新が動機）
  - 旧方針（Expo (React Native) + gomobile のモバイルネイティブ）は廃止
  - LinkSelf はブラウザ向け TypeScript 実装を使用する（`11_LinkSelf拡張要望.md`）
  - 地図は map-polygon-editor（DOM 前提）をそのまま流用できる（旧方針で必要だった MapLibre React Native への再実装は不要）
  - i18n catalog・訪問ダイアログ群は既存デスクトップ版 React 実装から移植
  - 前提制約: ブラウザはバックグラウンド実行ゼロのため、**前景起動時に差分同期完了 → タブ非表示・クローズで graceful stop** のライフサイクルを採用する（常時同期は想定しない）
  - LinkSelf 側に必要となる拡張（TS 実装、ブラウザ向けトランスポート、常時稼働ノード、高速起動、peerstore 永続化等）は `11_LinkSelf拡張要望.md` 参照

## 機能スコープの基本スタンス

- 活動メンバーロールの UI も **基本的に管理・編集ロール向けとほぼ同等の機能** を提供する（単一 PWA 内の権限ゲートで出し分ける）
- 「現場で必要な範囲」と「事務所で行うべき操作」の境界線は設計・実装・運用テストを経て段階的に明確化する
  - 例：貸出発行・強制回収などの管理操作はモバイル画面サイズでは誤操作リスクが高そうだが、確証は実運用で得る
  - 当面は管理・編集ロールと同等機能を提供し、**運用テストの結果に基づいて活動ロール・モバイル利用時に制限する項目を見極める**スタンスとする
  - 制限事項が固まり次第、本ドキュメントに明記する

## 区域

- 活動メンバーも区域一覧を閲覧できる
- 訪問記録の **入力** はチェックアウト経由を必須とする（`VisitRecord.CheckoutID` NOT NULL）。入力可能な区域は以下のいずれかを満たすもの
  - 自分が担当者となっているチェックアウト区域
  - 他のメンバーがチェックアウトしている区域に対し、有効な招待を受けている区域（区域招待、詳細は `05_チェックアウト.md`）
- 編集メンバー以上は **閲覧** はチェックアウト不要で全区域可能。**入力** したい場合は自分でチェックアウトするか、招待を受ける必要がある（詳細は `05_チェックアウト.md`）
- チェックアウト発行は活動メンバー・編集メンバー以上の双方が可能（操作種別「貸し出し／持ち出し」の区別は廃止済み、`05_チェックアウト.md`）
  - 活動メンバーは自分自身を担当者にしたチェックアウトを発行できる
  - 編集メンバーは任意のメンバー（自分含む）を担当者にしたチェックアウトを発行できる
  - 他者のアクティブなチェックアウトが無い区域であればチェックアウトできる（期間・対象区域親番による絞り込みは持たない）
- 各種申請（編集リクエスト＝要削除／要移動／その他、地図情報更新申請、訪問拒否宅報告）は、**入力権限を持つメンバー全員（担当者・被招待者・自身でチェックアウトした編集メンバー）が等しく発行できる**
  - 「現場で気づいた事実」を即座に編集メンバーへ届けるための経路であり、被招待者からの発行も同等に扱う
  - 申請の出所は `Request.UserID`（申請者 DID）で追跡する（追加の紐付けは持たない）
- 場所の**追加**は申請ではなく直接作成できる（詳細は後述「場所の直接追加」節・`07_通知と申請.md`「場所操作の権限」）。破壊的操作（削除・移動・情報修正）は直接不可でタスク起票とする非対称（編集メンバーであっても**タッチ端末利用時は同じ扱い**。直接操作は編集メンバー×非タッチ端末のみ）

## 訪問記録

- 活動メンバーが訪問内容や訪問場所の状況を記録する。
- 入力項目
  - 日時（ダイアログ起動時に自動入力、手動編集可）
  - 訪問ステータス（スピナー選択）
  - 訪問メモ（個人専用、自由記述）
  - 自前のタグ（個人用、検索・管理に利用）
- 共有/非共有の区分
  - **ネットワーク共有**: 日時・訪問ステータス（網羅状況の把握、再訪事故防止のため）
  - **個人専用（非共有）**: 訪問メモ、個人タグ
  - 共有情報も個人情報保護との兼ね合いを配慮する

### 訪問ステータス（スピナー選択肢）

戸建て・部屋いずれの訪問記録ダイアログでも以下の 5 択から選ぶ（集合住宅単位での記録は持たない。詳細は `## 訪問記録ダイアログ` 節）。

| ステータス | 性質 | 追加入力 | 後続処理 |
|---|---|---|---|
| 会えた | ネットワーク共有 | なし | 網羅判定、再訪間隔の参考データ |
| 留守 | ネットワーク共有 | なし | 網羅判定、他メンバーが再網羅可能 |
| 空き家（入居の可能性あり） | ネットワーク共有 | なし | 一時的な空室として扱う。再訪対象 |
| 空き家（廃屋）または更地 | ネットワーク共有 + 申請 | テキスト入力（必須／状況補足） | **地図情報更新申請**として編集メンバーのタスクへ登録 |
| 訪問を望まない | ネットワーク共有 + 申請 | テキスト入力（必須／状況補足） | **訪問拒否宅報告**として編集メンバーのタスクへ登録 |

- 申請を伴うステータス（「空き家（廃屋）または更地」「訪問を望まない」）は、選択直後にテキスト入力ダイアログを開く。テキスト入力をキャンセルした場合はステータス選択も既定値（「留守」）に戻す。
- ダイアログ起動時の初期選択は **「留守」**。理由は次のとおり。
  - 訪問結果として最も頻度が高いと想定される
  - ネットワーク共有のみで追加入力・申請を伴わない最も無害な選択肢
  - 「会えた」を初期値にすると押し間違いで誤った網羅判定が記録されるリスクがある
- 申請タスクの処理仕様（受理/却下、データ反映フロー等）は次期スコープで設計する（`07_通知と申請.md`）。

### 訪問記録のデータ構造

- 場所データ（NULL可）：場所モデルへの参照
- 座標（NULL可）：場所モデル未登録の地点にも記録可能
- 場所追加申請は場所＝NULLで座標必須
- **場所も座標も持たない訪問記録**は本スコープでは扱わない（`09_継続的検討事項.md` 参照、別途検討）

### 訪問記録の修正・削除

- 活動メンバーは誤入力した訪問記録を修正・削除できる
- 管理アプリからも編集可能（上位互換）
- 編集履歴を保持する

## 訪問記録ダイアログ

地図上の場所アイコンをタップして開くダイアログ。戸建て／集合住宅／部屋（集合住宅内）で構成が異なる。

### 読み取り／編集モード

ダイアログの挙動は、開いた場所の **有効モード**（区域レベル ∩ 場所レベル、`05_チェックアウト.md`「アクセスモード」節）によって以下のように切り替わる：

- **editable モード**（通常）
  - 入力エリア（日時、訪問ステータス・スピナー、訪問メモ）は通常表示・編集可
  - 「保存」ボタンで訪問記録を作成
- **read-only モード**
  - 入力エリアは表示せず、参考情報のみを表示
    - 場所の `Label` ／ `Address` ／ `Description`（集合住宅）
    - 「最近会えた日付（ネットワーク全体）」「自分の訪問履歴」セクション
  - 「保存」ボタンの代わりに **「この区域をチェックアウトして記録する」CTA**（区域レベルが read-only の場合）を表示
  - 場所レベルのみ read-only の場合は CTA は表示せず、「この場所は読み取り専用です」と簡潔に案内する（用途は `05_チェックアウト.md` 参照）
  - 「編集をリクエスト」ボタンは read-only モードでも有効。観察した事実の申請経路は記録権限と独立して機能する（編集メンバーが閲覧中に気づいた変化、被招待者が期限切れ後に再訪して気づいた変化なども申請できる）。申請の出所は `Request.UserID` で追跡し、不適切な申請は編集メンバーが却下する

以下の各ダイアログ仕様は editable モードを前提とした記述。read-only モードでの差分は上記の通り共通。

### 戸建て訪問ダイアログ（`Place.Type == "house"`）

- 起動: 地図上の戸建てアイコン（青）をタップ
- 上部: 場所の `Label`（名前、未入力なら「名前なし」）と `Address`
- 入力エリア
  - 日時（自動入力、編集可）
  - 訪問ステータス（スピナー、5択は前述）
  - 訪問メモ（テキスト入力、個人専用）
- 参考情報「最近会えた日付（ネットワーク全体）」
  - 対象は **「会えた」記録のみ**
  - 表示は **日付のみ**（例: `2026/04/15 に会えた`）。時刻・訪問者名は表示しない。区切りはスラッシュ統一
  - 経過日数で色分け
    - **1ヶ月以内: 赤文字**（再訪間隔が近すぎる警告）
    - **半年以内: オレンジ文字**
    - **それ以上: 黒文字**
  - ネットワーク全体で「会えた」記録が一度もない場合は「会えた記録なし」と表示
- 自分の訪問履歴セクション（折りたたみ可、初期は折りたたみ）
  - 同一場所に対する自分の訪問記録を時系列降順で一覧表示
  - 履歴がなければ「自分の訪問履歴なし」と表示
- ダイアログ下部「**編集をリクエスト**」ボタン（戸建て・集合住宅で UI 共通）
  - クリックで編集リクエストダイアログを開く。**種別（要削除／要移動／その他）**を選び、**詳細テキスト**を入力する（種別の既定は「その他」）
  - 種別と `RequestType` の対応: 要削除→`place_delete` / 要移動→`place_move` / その他→`place_info_modify`（`07_通知と申請.md`「場所操作の権限」）
  - 直接編集権限（編集メンバー以上×非タッチ端末）を持たない利用時は場所を直接 削除・移動・編集できないため、いずれもこのリクエスト経由とする（誤操作防止）。直接編集権限がある場合もボタンは表示したままでよい（直接編集は地図の右クリックメニューから行う）
  - 申請であり即時更新ではない（次期スコープ、現フェーズはデータ保持のみ）
- 保存・キャンセル
  - 保存: 訪問記録を作成。スピナーが申請を伴うステータスの場合、テキスト入力後に同時に申請データも作成
  - キャンセル: すべて破棄

### 集合住宅訪問ダイアログ（`Place.Type == "building"`）

- 起動: 地図上の集合住宅アイコン（オレンジ）をタップ
- 集合住宅自体には**スピナーを持たない**（建物単位の訪問ステータスは記録しない）
- 上部: `Label`（名前）と `Address`
- **Description 表示**: `Place.Description` が非空（length > 0）の場合、上部の見やすい位置に表示する
  - 編集メンバーが集合住宅編集ダイアログで設定する補足情報（注意事項、訪問時の留意点など）
  - `Description` フィールド自体の仕様は `03_地図機能.md` の「集合住宅の追加・編集」節に追記
- 部屋番号一覧
  - 当該集合住宅の Room 一覧を `SortOrder` 昇順で表示
  - 行表示: 部屋番号（`DisplayName`）+ 自分の最終訪問日（あれば、戸建てと同じ色分けルール）
  - 行タップで **部屋訪問ダイアログ**（戸建て訪問ダイアログと同等構成）を開く
- ダイアログ下部「**編集をリクエスト**」ボタン（戸建てと UI 共通）
  - 種別（要削除／要移動／その他）を選び詳細テキストを入力
  - 用途例: 部屋番号の修正（その他）、建物が取り壊された（要削除）、位置がずれている（要移動）、入口の変更（その他）など
  - 集合住宅の削除・移動・編集も直接不可・リクエスト経由（`RequestType` 対応は戸建てと同じ）

### 部屋訪問ダイアログ（`Place.Type == "room"`）

- 起動: 集合住宅訪問ダイアログ内の部屋行タップ
- 構成は戸建て訪問ダイアログと同一（スピナー、メモ、参考情報、自分の履歴、修正申請ボタン）
- 上部表示は親建物の名前と部屋番号を半角スペース区切りで連結（例: `○○マンション 101`）。部屋番号は数字とは限らない（`A棟203` 等）ため「号室」等の接尾辞は付けない。

### 場所の直接追加

一般スタッフ（活動メンバー）も、活動中に見つけた未登録の建物を**直接 `Place` として作成できる**（旧「場所作成申請」を廃止し直接作成に切替。`07_通知と申請.md`「場所操作の権限」）。

- 起動: 訪問記録画面の地図上で **空白部分をロングタップ**（場所アイコン上のロングタップは無視）
- ロングタップ位置に **「家を追加」「集合住宅を追加」** の選択メニュー（直接編集の右クリックと同じコンテキストメニュー UI を流用）を表示する
  - **家を追加** → 家追加ダイアログ（`AddPlaceInputDialog`、住所・名前を任意入力）→ 保存で `Place`（`Type="house"`）を直接作成
  - **集合住宅を追加** → 集合住宅ダイアログ（`BuildingEditDialog` 新規モード）→ 保存で `Place`（`Type="building"`）と部屋を直接作成（`03_地図機能.md`「集合住宅の追加・編集」に準拠）
- 座標はロングタップ位置から自動取得。作成先は訪問中の当該区域（`areaId`）
- **ポリゴン外でも作成できる**（直接編集の右クリック追加の「区域内のみ」制約は適用しない）。訪問中はどの区域で活動しているかが定まっているため当該区域へ帰属させ、編集メンバーが後で帰属を修正できる（`03_地図機能.md`「住宅マーカーの区域帰属」）
- 直接作成のため編集メンバーの事後承認は不要。専用の通知・タスクも設けない（不適切な場所は編集メンバーが削除機能で無効化）
- 「その他」種別は廃止する（`Place.Type` に対応がなく、直接作成では家／集合住宅のみ扱う。店舗・公共施設等の種別定義は `09_継続的検討事項.md`）
- ロングタップによる誤操作防止 UX は別途検討（`09_継続的検討事項.md`）
- 5m 以内の削除済み場所との訪問記録紐付け（復元確認）は本パスでは行わない（編集メンバーの直接編集（右クリック追加・移動）で扱う。`03_地図機能.md`「場所の論理削除と訪問記録の紐付け」）

## 訪問記録画面

訪問ダイアログを起動するための地図画面。ダッシュボードを唯一の入口とし、左サイドバーに独立メニューは設けない。

### 入口

- どのロール・どの端末でも **ダッシュボードに統合**（独立メニューを設けない）
  - 「アクセス可能な区域」セクション（全ロール）：自分が担当者となっているチェックアウト＋有効な招待を受けた他者のチェックアウト
  - 「チェックアウト可能な区域」セクション（全ロール）：まだ自分が担当しておらず、他者のアクティブチェックアウトもない区域（行内ボタンで即時チェックアウト発行）
  - 「全ての区域一覧」セクション（編集メンバー以上のみ）：チェックアウトの有無にかかわらず全区域へアクセス可能（上位互換）。モバイルでも提供する
  - いずれの行からも当該区域の訪問記録画面へ遷移する
  - チェックアウト可能な区域が無いときは「チェックアウト可能な区域はありません」と案内
  - 詳細レイアウトは `10_画面設計.md` のダッシュボード節を参照
- モバイル利用時（狭幅レイアウト）の補足
  - モバイル UI に合わせてセクションは縦スタックで配置し、「全ての区域一覧」はフィルタ操作前提でデフォルト折りたたみ等の省スペース表示を検討する
  - 入力動線（チェックアウト不在時の CTA、強制回収・招待依頼の分岐）はデスクトップ表示と同等に提供する

### 起動後の遷移

- **最終形**: ダッシュボードの該当区域行から、当該区域の地図画面に直接遷移する（アクセス権は遷移先画面で再検証）
- **Phase 1 暫定**: チェックアウトモデルが未設計のため、ダッシュボードからの遷移経路は仮実装。ポリゴン紐付け済みの区域 `NRT-001-01` の地図に固定遷移する
  - チェックアウト関連の本実装着手時に最終形へ移行する
  - 訪問記録保存も Checkout を介さず `RecordVisitPhase1(actorID, areaID, ...)` でダイレクトに作成する暫定 API を使用（Checkout 配線完了時に通常 `RecordVisit` へ統合）

### アクセス条件（2026-07-14 場所編集画面統合に伴い明文化）

- **活動メンバー**: 以下のいずれかを満たす区域の訪問記録画面のみアクセスできる
  - 自分が担当者となっている active チェックアウト
  - 他者のチェックアウト区域への有効な区域招待（`05_チェックアウト.md`）
  - 満たさない区域はアクセス不可（ダッシュボードにも入口行が出ない。URL 直打ちは画面側で拒否しダッシュボードへ誘導）
- **編集メンバー以上**: いつでも全区域にアクセスできる（チェックアウト不要。ダッシュボードの「全ての区域一覧」からも遷移できる）
  - ただし**訪問記録の入力**には従来どおり自分の active チェックアウトまたは招待が必要（「区域」節。閲覧・場所編集とは独立）

### 地図 UI

- 表示密度は `03_地図機能.md` の「場所の直接編集」と同等（場所アイコン、通し番号バッジ、対象区域輪郭の濃色表示など）
- **場所編集機能を本画面に統合する**（2026-07-14: 場所編集専用画面〔区域詳細編集〕を廃止）
  - **直接編集権限**（追加＋削除・移動・情報修正の全直接操作）＝ **編集メンバー以上 × 非タッチ端末**のときのみ。右クリックコンテキストメニュー（家を追加／集合住宅を追加／場所編集／移動／削除）を提供する（`03_地図機能.md`「場所の直接編集」）
  - それ以外（活動メンバー全端末・編集メンバー×タッチ端末）は**追加のみ直接**、削除・移動・情報修正は申請（`07_通知と申請.md`「場所操作の権限」）
  - ポリゴン編集は本画面では提供しない（区域編集画面 `/map` のみ）
- **場所一覧と訪問記録の一覧 UI** を設ける（広幅=右ペイン／狭幅=全面オーバーレイ。詳細は `03_地図機能.md`「場所一覧と訪問記録の一覧」）
- 共通の地図ビュー部品を再利用するか専用部品とするかは実装フェーズで判断する

### 操作仕様

- **タップ**（マウスクリック / 単指タップ）
  - 戸建てアイコン → 戸建て訪問ダイアログ
  - 集合住宅アイコン → 集合住宅訪問ダイアログ
  - 空白タップ → 何もしない（誤操作で記録を作らないため）
- **ロングタップ**（モバイル長押し / マウス右クリック）
  - 場所アイコン上 →
    - 直接編集権限あり（編集メンバー×非タッチ）: コンテキストメニュー「場所編集」「移動」「削除」（`03_地図機能.md`「場所の直接編集」）
    - 直接編集権限なし: 何もしない（ドラッグ移動・直接削除は提供しない。削除・編集は訪問ダイアログ内の申請ボタンから）
  - **空白部分** → 「家を追加／集合住宅を追加」選択メニュー → 場所を直接作成（前述「場所の直接追加」節。全ロール共通）
  - ロングタップは編集系の代替には使わない（モバイル UX 低下のため原則使わない方針の例外として、場所の直接追加のみ採用）
- **マップ操作**: パン・ピンチズームは標準。ズーム制限は `03_地図機能.md`「場所の直接編集」と同等

## 最新の状況

- 状況の変化
  - 建物が取り壊されて更地になっている
  - 以前は住んでいた家が廃屋、空き室になっている。
  - 更地に新築
  - 1つまたは複数の更地または戸建てが集合住宅に建て替わった。
  - 外国人居住情報
    - 言語によっては専従メンバーが訪問できるように情報を切り分ける
- 簡易な情報は活動メンバーが記入できる
  - 表札名が空欄だったところに入力、変更など
  - 集合住宅が新築されたときなどは「地図情報更新申請」を投稿できる
    - 申請を受けて編集メンバーが詳細情報を調査する
- 場所データの追加
  - 活動メンバーが新築等で場所モデルにない地点を **直接追加できる**（旧「事後承認・申請タスク化」を廃止。前述「場所の直接追加」節・`07_通知と申請.md`「場所操作の権限」）
  - 直接反映のため事前・事後の承認は不要。専用の通知・レビュータスクも設けない
  - 不適切な場所データ（建物が建たない場所など）は編集メンバーが地図・場所一覧で気づき、**既存の削除機能で無効化（論理削除）**する
    - 無効化時、その場所に紐づく訪問記録は編集メンバー権限で破棄される（確認UIが必要）
  - 削除・移動・編集は一般スタッフの直接操作を認めず、「編集をリクエスト」（要削除／要移動／その他）として起票する（誤操作防止）
- 訪問をしないお家
  - 住人または関係者の意思表示、または危険な状況により一定期間訪問しないほうが良い場所を報告する
  - 編集メンバーはその情報を精査して区域に反映する
    - このデータ反映は権限者が行う
  - 訪問不可状態の解除
    - 編集メンバーは地図上で訪問拒否宅の詳細を確認できる。
      - 別途規定するガイドラインに則り訪問再開の可否を判断し編集できる。
