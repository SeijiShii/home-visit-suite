# 通知と申請

## 通知

- 任命招待
  - 招待を受けた人が視認できる箇所に表示する
- 区域のチェックアウト
  - 担当者となった人のマイページに表示される
  - 返却・回収後の区域は「返却済み」として一定期間（1か月）表示する
  - 自分自身がチェックアウト操作した区域も同様にマイページに表示される
- 区域招待
  - 招待 **発行時のみ** 被招待者のマイページに通知する
  - チェックアウト返却・回収による失効、招待の手動取消、期限切れは通知しない（ダッシュボードの「アクセス可能な区域」セクションに残時間と状態を表示することで補う）
  - 通知ノイズを抑えるための最小構成。詳細仕様は `05_チェックアウト.md` の「区域招待」節を参照
- 申請
  - 編集メンバーのタスクリストに表示される
  - 申請結果が受理されたかどうかは申請者は関知しない（データ反映をもって受理とする）

## 申請内容の取扱い

- 活動メンバーからの申請内容を区域に反映する
  - 区域情報の更新
  - 訪問をしない家や場所
    - タスクとして管理する
      - 未処理、保留、処理済み
- 「訪問しない家」の期限管理
  - システム側で期限の仕組みを定義しない
  - 運用者側で期間や判定基準を持つ

## 場所操作の権限（ロール × 端末）

訪問記録画面（2026-07-14 から場所編集を兼ねる。`08_活動メンバー向けアプリ.md`）における場所操作は、**加算的操作は直接・破壊的操作はタスク起票**の非対称とする。誤操作で既存データ（訪問記録の紐付き等）を失う破壊的操作だけを「精密操作ができる環境の編集メンバー」の手に残し、低リスクな追加は現場で即反映できるようにする趣旨。

**直接編集権限 ＝ 編集メンバー以上 × 非タッチ端末** のときのみ。タッチ端末判定は `matchMedia("(pointer: coarse) and (hover: none)")`（`03_地図機能.md`「画面構成」）。

| 操作 | 編集メンバー以上 × 非タッチ端末 | それ以外（活動メンバー全端末／編集メンバー × タッチ端末） |
|---|---|---|
| 場所の追加 | 直接作成（右クリック「家／集合住宅を追加」またはロングタップ） | **直接作成できる**（空白ロングタップ →「家／集合住宅」。編集メンバーの事後承認を要さない） |
| 場所の削除・移動・修正 | **直接操作できる**（場所アイコン右クリック →「場所編集」「移動」「削除」） | 直接不可。**編集リクエスト**を起票（訪問ダイアログ下部「編集をリクエスト」→ 種別〔要削除／要移動／その他〕＋詳細テキスト） |
| ドラッグ移動・直接削除 | 移動はクリック追従方式（`03_地図機能.md`「場所の直接編集」） | **提供しない**（誤操作防止。場所アイコンの長押し・ドラッグは無反応） |
| **部屋（Room）の追加・部屋番号編集・削除** | 直接操作できる（集合住宅編集ダイアログ／集合住宅訪問ダイアログ） | **直接操作できる**（集合住宅訪問ダイアログから。2026-07-17 例外追加） |

- **部屋の例外**（2026-07-17）: 部屋の追加・部屋番号編集・削除は「破壊的操作はタスク起票」の対象外とし、全メンバー・全端末（タッチ含む）が集合住宅訪問ダイアログから直接行える。根拠: (1) いずれもボタン＋入力のみでドラッグ操作を含まず誤操作が起きにくい、(2) 削除は論理削除であり、同じ部屋番号を追加し直せば同一 `Place` として復元され訪問記録の紐付きを失わない（`03_地図機能.md`「部屋（Room）の同番号復元」）。建物（Building）自体や戸建ての削除・移動・修正は従来どおり編集リクエスト経由。

- 編集リクエストの種別と申請種別（`RequestType`）の対応:
  - **要削除** → `place_delete`（場所の無効化＝論理削除の依頼）
  - **要移動** → `place_move`（位置ずれの是正依頼）
  - **その他**（既定） → `place_info_modify`（表札名・部屋番号などの情報修正依頼）
- 編集リクエストは**編集対象の場所 ID（`Request.placeId`）と区域 ID（`Request.areaId`）を保持して発行する**。これにより編集メンバーはタスク一覧（`RequestsPage`）から当該場所の**訪問記録画面（直接編集を兼ねる）へ直接遷移**できる（遷移導線は申請一覧の行に実装済み。下記「申請一覧」2026-07-16）。

- 直接追加した場所には専用の通知・レビュータスクを設けない。不適切な場所（建物が建たない地点等）は編集メンバーが地図・場所一覧で気づき、**既存の削除機能で無効化（論理削除）**する（`08_活動メンバー向けアプリ.md`「最新の状況」）。
- 編集メンバーは訪問記録画面の直接編集（非タッチ端末利用時）で従来通り 追加・移動・削除・編集を直接行える。編集リクエスト（要削除／要移動／その他）を受けて実データへ反映する。
- 旧「場所作成申請（`place_add`）」は本変更で廃止した（追加を直接作成に切替）。

## 申請種別

訪問ダイアログから発行される申請の種別を定義する。詳細仕様は `08_活動メンバー向けアプリ.md` の「訪問記録ダイアログ」節を参照。

| 申請種別 | 起動経路 | 入力 | 編集メンバー側の処理 |
|---|---|---|---|
| 場所削除申請（要削除, `place_delete`） | 戸建て・集合住宅訪問ダイアログ下部「編集をリクエスト」→ 種別「要削除」 | 詳細テキスト（**任意**）、対象 PlaceID | 現地確認の上、場所の無効化（論理削除）を判断 |
| 場所移動申請（要移動, `place_move`） | 同上 → 種別「要移動」 | 詳細テキスト（正しい位置の説明）、対象 PlaceID | 場所の座標を修正 |
| 場所情報修正申請（その他, `place_info_modify`） | 同上 → 種別「その他」（既定） | 詳細テキスト、対象 PlaceID | 表札名・部屋番号などの修正を検討 |
| 地図情報更新申請（`map_update`） | 訪問ダイアログのスピナー「空き家（廃屋）または更地」選択時 | テキスト入力 | 場所の無効化・更地化・新築への置換等を検討 |
| 訪問拒否宅報告（`do_not_visit`） | 訪問ダイアログのスピナー「訪問を望まない」選択時 | テキスト入力 | 当該場所を訪問不可状態に設定するか精査 |

- 「編集をリクエスト」の詳細テキストは原則必須。ただし**要削除のみ任意**（削除理由は自明なことが多く入力を強制しない。2026-07-16）。既定の種別は「その他」。

- いずれの申請も編集メンバーのタスクリストに表示される（前述「通知」節）
- 申請者は受理結果を関知しない（データ反映または無視をもって完結）
- 申請の状態管理（未処理/保留/処理済み）と申請一覧 UI は実装済み（下記「申請一覧」。2026-07-16）。却下フロー、申請者への通知などは次期スコープで設計する

## 申請一覧（`/requests`）

編集メンバー以上がアクセスする申請管理画面（`10_画面設計.md` §7）。

- 全区域の申請を**単一リスト**で表示する（未処理/処理済みのセクション分けはしない。ステータスバッジで区別する。2026-07-16）
- ステータスは **未処理（`pending`）/ 保留（`on_hold`）/ 処理済み（`resolved`）** の 3 値
- 行の表示項目: 申請種別、区域識別子（`領域-区域親番-区域`）、**申請者名**（表示名で解決。解決できない場合は ID をそのまま表示）、申請日、詳細テキスト、ステータスバッジ、処理日（処理済みのみ）
- 絞り込み・検索（組み合わせはすべて AND）:
  - **ステータス絞り込み**（複数選択可）。**初期表示は未処理のみ**
  - **テキスト検索**: 区域識別子（例 `NRT-001-05`）・領域名・区域親番名にマッチ（大文字小文字を区別しない部分一致）
  - **申請日（createdAt）・処理日（resolvedAt）の期間絞り込み**（それぞれ from/to）
- ステータス変更: 行内の操作で他の 2 ステータスへ変更できる（未処理⇄保留⇄処理済み）。処理済みへの変更で `resolvedAt`/`resolvedBy` を記録し、処理済みから他ステータスへ戻すと消去する
- **申請対象への遷移**（2026-07-16）: 行の「訪問記録へ」で当該区域の訪問記録画面（`/visits/:areaId`）へ遷移する。`placeId` を保持する申請は `?place=<placeId>` で**対象の場所を選択状態**（地図マーカー強調＋場所一覧の行ハイライト）で開く。**部屋（`room`）を対象とする申請は親の集合住宅に読み替えて選択する**（部屋自体はマーカー・一覧行を持たないため）。`areaId` を持たない申請には遷移操作を出さない
- 申請データ（`requests` テーブル）は ScopeNetwork で全メンバーへ同期される（`01_共通基盤.md`「同期スコープ」）。受信適用時、開いている申請一覧は自動更新される

## 監査ログ

- 権限変更・区域編集・訪問不可設定などの重要操作の履歴を記録する
- 管理者・編集メンバーが閲覧できる
- チェックアウトの強制回収・担当者変更・招待発行/取消は監査対象

## データ保持・アーカイブ

- LinkSelfの設定値として保持期間を管理者が設定できる
- 管理者はLinkSelfデータをダンプできる
