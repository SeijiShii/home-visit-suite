# 継続的検討事項

## 権限（解決済み）

- 編集メンバーが稼働できないときに活動メンバーだけで区域を取得できるように限定的な権限範囲の追加が必要か
  - → 「持ち出し可能区域」の仕組みで解決。編集メンバーが事前に持ち出し可能区域を設定しておけば、活動メンバーが自主的に区域を取得できる
  - 詳細は「05_チェックアウト.md — 区域の貸し出し（チェックアウト）モデル」を参照

## 招待された活動メンバーの再訪問ニーズ（ペンディング）

- 区域招待（`05_チェックアウト.md`）で招待された活動メンバーが、当該区域で活動中に「後日改めて訪問したい場所」を発見するケースの扱いは未決定
- 必要性
  - 招待の有効期限切れ後にも、被招待者が当該場所の情報を**参照**したり、**個人記録（個人メモ・個人タグ等）を追加**したりしたい場面がある
  - 例: 「会えなかったが在宅予定の時間帯を聞いたので後日寄ってみたい」「外国語対応で再訪が必要」など、招待単位の活動で完結しない継続的フォロー
- 想定される論点
  - 期限切れ後にどの情報をどこまで参照可能にするか（場所情報のみ／自分の過去訪問記録のみ／全訪問記録、等）
  - 期限切れ後に追加できるのは個人スコープ（`PersonalNote` / 個人タグ）のみとするか、ネットワーク共有の訪問記録追加まで許すか
  - 個人記録のみ許可する場合、その入口 UI（区域からはアクセスできない前提で、場所単位の個人ノート画面など）
  - 招待延長／再招待ワークフローと、担当者・編集メンバーへの再訪要望の通知
  - 担当者本人による再訪問との重複・衝突の調整
- **設計の流用予定**: 期限切れ後の特定場所アクセスは `05_チェックアウト.md` の「場所レベル read-only モード」（場所単位のアクセスモデル）を流用して実現する想定。場所レベルのモデルは現フェーズで先行整備済み（既定 editable）、UI からの切替操作は本ペンディングと併せて設計する。
- 本フェーズではスコープ外。チェックアウトモデル本実装後に再検討する

## 区域系画面の権限切り分け

- 区域編集・区域詳細編集など区域系画面の利用可能ロールを別途整理する
- 例: 区域詳細編集を編集メンバー以上に限定するか、活動メンバーは閲覧のみとするか等
- 訪問記録画面（`08_活動メンバー向けアプリ.md`）は全ロール利用可で確定済み

## 場所も座標もない訪問記録の扱い

- 旧仕様で「場所も座標も持たない訪問記録」を活動メンバーの個人データとして許容していたが、本フェーズではスコープ外とした
- 必要性（GPS取得失敗時の救済、純粋な個人メモ用途等）と、訪問記録メニューからの起動経路を別途設計する

## 場所作成申請の「その他」種別の定義

- 場所作成申請ダイアログの種別選択肢「その他」（家・集合住宅以外）の正式定義を別途検討
- 想定される対象: 店舗、公共施設、事業所、寺社、学校など
- 「その他」をさらに細分化するか、自由記述に委ねるかも論点

## ロングタップによる場所作成申請の誤操作防止 UX

- 訪問記録画面では原則ロングタップを使わない方針に対して、場所作成申請のみ例外的にロングタップで起動する
- モバイルでの誤操作（地図操作中の意図しないロングタップ）を防ぐ UX を別途検討
- 候補: 確認ダイアログを必ず挟む、長押し時間を通常より長く設定、起動前にトースト/ヘルプを出す等

## 訪問記録画面の Phase 1 暫定実装の解消

- Phase 1 では以下を暫定として実装している
  - チェックアウト中区域一覧 → 区域選択の遷移はなく、`NRT-001-01` へ固定遷移する
  - `actorId`（自分の DID）の取得経路が未配線（空文字を渡している）
  - `CheckoutID` も未配線（空文字で `RecordVisit` を呼んでおりサービス側のチェックは将来対応）
  - 場所作成申請・場所修正申請の永続化は console.log のみ（RequestService 経由の保存は次期スコープ）
- 地図表示は実装済み（区域詳細編集と同等のビュー、編集操作なし）。`useAreaDetailMap` フックで両画面が共通化されている。
- 解消には以下が必要:
  - チェックアウトモデルの実装（`05_チェックアウト.md`）
  - LinkSelf 個人 DID 取得経路の整備
  - Request 永続化用のサービスとバインディング

## 訪問活動概念廃止に伴うコード反映（実装側の積み残し）

仕様書は 2026-05-04 に「訪問活動 (Activity) / 訪問活動チーム (Team) / ActivityTeamAssignment」を廃止し、`05_チェックアウト.md` に集約済み。実装は未追従で旧概念が残っているため、チェックアウト本実装の着手時に同時にリネーム・削除する。

- `shared/domain/models/visit.go`
  - `Team`, `ActivityTeamAssignment` 構造体を削除
  - `Activity` → `Checkout`、`ActivityStatus` → `CheckoutStatus` にリネーム（リネームせずに名前のみ既存運用も可、判断は実装着手時）
  - `VisitRecord.ActivityID` → `CheckoutID`（Phase 1 で空文字許容のため互換不要）
- `shared/domain/activity_repository.go`（`ActivityRepository`）
  - Team 系メソッド `ListTeams/GetTeam/SaveTeam/DeleteTeam` を削除
  - Assignment 系メソッド `ListAssignments/SaveAssignment/DeleteAssignment` を削除
  - リポジトリ自体を `CheckoutRepository` 系へリネーム検討
- `shared/service/activity.go`（`ActivityService`）／`activity_impl.go`
  - `AssignTeam` メソッド削除
  - サービス名を `CheckoutService` へリネーム検討
  - 担当者変更系として `ReassignOwner`（編集メンバー専用）を新設
- `desktop/main.go` の DI 配線および `desktop/internal/binding/visit.go` の DI 受け取り型を追従（Team 直接参照はないため軽微）
- Wails Binding 名: `ActivityBinding` → `CheckoutBinding`、メソッド `ListActivities/GetActivity` → `ListCheckouts/GetCheckout`
- DB スキーマは Phase 1 のため新規作成で対応（`teams`, `activity_assignments` テーブルは作成しない／`activities` → `checkouts` テーブル名で作る）
- 区域招待（`checkout_invitations`）の追加実装も同タイミングで行う：モデル `CheckoutInvitation`（`CheckoutID, InviteeID, InviterID, ExpiresAt, RevokedAt`）、リポジトリ、サービスメソッド `Invite/RevokeInvite/ListInvitations`、有効期限切れ判定はクエリ時に評価。
  - アクセス可否判定は閲覧／入力／場所単位の3レイヤーで構成する。
    - `CanViewArea(userID, areaID)`: 「編集メンバー以上 OR 入力可能」
    - `AreaAccessMode(userID, areaID)`: editable / read-only を返す。「当該区域に自分が関与する `active` チェックアウトが存在する＝担当者 OR 有効な招待保有」なら editable、それ以外は read-only。
    - `PlaceAccessMode(userID, placeID)`: editable / read-only を返す。場所単位の特殊状態を反映する（既定値 editable、現フェーズではモデルのみ用意し UI からの切替は未実装）。
    - `EffectiveAccessMode(userID, placeID)`: 上記2つの AND（より制限的な側）を返す。訪問記録の保存・編集はこれが editable のときのみ許可する。
  - 招待発行は `active` チェックアウトのみ許容（サービス層でバリデーション）。
  - 招待取消は「招待者本人 OR 当該チェックアウトの現担当者 OR 編集メンバー以上」のいずれか。担当者変更時に既存の未失効招待は維持する（`InviterID` も付け替えない）。
  - チェックアウト返却・回収時、紐づく未失効招待を一括失効する（`RevokedAt` 設定 or 期限切れ扱い）。
  - 詳細仕様は `05_チェックアウト.md` の「区域へのアクセス権」「区域招待」「入力動線」節を参照。
- `VisitRecord.CheckoutID` は **NOT NULL** とする。Phase 1 暫定 API `RecordVisitPhase1` のみ NULL/空文字許容で先行運用し、本実装移行時に NOT NULL 制約を導入する。マイグレーションは Phase 1 段階のため新規スキーマで対応可能。
- 編集メンバー以上の入力動線：訪問記録画面で active チェックアウトを持たない区域に入った場合、入力をブロックして「この区域をチェックアウトして記録する」CTA を表示する。CTA から：
  - active チェックアウトなし → 即時 `Checkout(lending, owner=自分, lentBy=自分)` を発行（自分自身への貸し出し）
  - 他者の active チェックアウトあり → 「招待を依頼」or 「強制回収して自分でチェックアウト」の2分岐 UI を提示。強制回収は監査ログ対象。
- 可用性バリデーションのロール分岐：`Checkout` サービスは活動メンバーの貸し出し／持ち出し操作にのみスコープ・貸し出し可能・持ち出し可能制約を適用する。編集メンバー以上はバイパス可能（上位互換）。実装上は `Checkout(actorID, ...)` のロール判定で分岐する。
- 訪問記録画面への入口をダッシュボードに統合する（`10_画面設計.md` ／ `08_活動メンバー向けアプリ.md`）。サイドバーの「訪問記録」独立メニューは廃止し、ダッシュボードに「アクセス可能な区域」セクション（全ロール）と「全ての区域一覧」セクション（編集メンバー以上のみ）を新設する。Bindingメソッドとして `CheckoutBinding.ListAccessibleAreas(myDID)` を新設、`RegionBinding.ListAreas(filter)` を全区域一覧用に流用する。
