## 自己端末の削除の仕様（2026-07-15 検討中・ユーザー判断待ち）

現状: デバイス一覧の「削除」はローカル登録簿（localStorage）の行を消すのみで、ロスター失効も相手端末への伝播も無い。ロスター由来行は削除不可。

前提の整理（現行設計での削除の意味）:
- グループ所属は**ユーザー DID 単位**。端末はロスター経由でその DID の配送先になるだけ
- ロスターから外れた端末は配送・devicesync の対象外になる＝**データは端末内に残るが以後更新されない「孤立化」**。同じユーザー鍵を持ち続けるため「他 ID の端末」に自動的になることはない
- 鍵が端末に残る以上、ロスター除外は協調的な措置であり暗号学的失効ではない（本気の失効は鍵ローテーションが必要）

必要とされた仕様（2026-07-15 ユーザー要望）: 削除時に以下を選択できる仕組み
- (a) **端末データも消す**: 対象端末のローカルデータを削除し、LinkSelf グループからも外す（リモートワイプ。対象端末がオンライン時は即時、オフライン時は次回接続時に best-effort）
- (b) **他 ID の端末としてグループに残す**: 対象端末を新しいユーザー DID として独立させ、グループのメンバーとして存続させる

未決事項（1 問ずつ確認して確定する）: ワイプの範囲（全初期化 vs 対象グループのみ）、(b) の成立方法（削除時の自動招待＝管理者のみ可 / 参加申請フロー）、非管理者が削除操作するときの (b) の扱い、ワイプ指示の配送手段（store-and-forward）と悪用ガード
- OPFS のグループ DB（`hvs-group-<slotId>.db`）の物理削除は sqlite-wasm（SAHPool VFS）に削除 API が無く現状不可。purge 時に `hvs.orphanGroupDbs` へ孤児として記録し、link-self 側の unlink API 導入後に掃除する（脱退フロー手順 3「ローカル DB 削除」の暫定制約）
- **グループ解散のブロードキャストは採用しない**（2026-07-15 決定。最後の管理者は残メンバーがいる限り脱退不可のガードで管理者 0 人グループを防ぐ。サーバーレス P2P に全端末レプリカのリモート消去手段が存在しないため、「解散で全員のローカル DB を消す」は保証できない）

- Wails Binding: `CheckoutBinding` 新設、`IdentityBinding` 新設（dev モード切替）
- フロントエンド: サイドバー整理（ロール別ガード）、ダッシュボード「アクセス可能な区域」「全ての区域一覧」、`CheckoutsPage` 本実装、`InviteDialog`、訪問記録画面の二層 read-only モード

2026-05-06 の仕様改訂により、可用性モデルは大きく変更:

- 旧: スコープ／貸し出し可能／持ち出し可能の階層 + 編集メンバーバイパス
- 新: AvailablePeriod の対象区域親番リストによる単純制約（編集メンバーバイパスなし）
- フィールド名リネーム: `OwnerID` → `PersonInChargeID`、`LentByID` → `CheckedOutByID`、`Type`（lending/self_take）削除

可用性バリデーション本体（AvailablePeriod 対象区域親番制約・期間アクティブ判定）は CheckoutService.Checkout で実装済み（2026-05-07）。
- アクティブ期間が存在しなければ `ErrInvalidState`
- 区域の親番が AvailablePeriod の対象に含まれなければ `ErrPermissionDenied`（編集メンバーもバイパス不可）
- 発行成功時は `Checkout.AvailablePeriodID` に当時のアクティブ期間 ID を記録する

期間終了による強制クローズは `AvailablePeriodService.ForceCloseExpiredCheckouts` として実装済み（バックグラウンド呼び出しタイミングは未配線）。
