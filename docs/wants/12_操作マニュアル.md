# 操作マニュアル

アプリの全機能を対象とした利用者向け操作マニュアルと、それを**低コストで最新に保つ**ための仕組み。

## 方針

マニュアルが陳腐化する原因は「実装を変えたときにマニュアルのどこを直すべきか分からない」ことにある。
そこで本仕組みは、**本文（人／AI が書く）と、それ以外すべて（機械が回す）** を分離する。

| 対象 | 担当 | 根拠 |
|---|---|---|
| スクリーンショットの撮影 | 機械（Playwright） | UI 改修のたびに撮り直しが無料になる |
| Markdown → HTML 変換・トピック ID の型生成 | 機械（ビルド） | リンク切れを型エラーとして落とす |
| 陳腐化の検知（どのページが古いか） | 機械（digest 照合） | 「どこを直すか」を人が探さなくてよい |
| リンク・参照の健全性検査 | 機械（`manual:check`） | 画面追加時のマニュアル漏れを検出 |
| 本文の執筆・更新 | 人／AI スキル | 自然言語は機械生成できない |

## 構成

```
docs/manual/ja/NN-<topic>.md      本文の SoT（Markdown + frontmatter）
pwa/public/manual/shots/<id>.png  スクリーンショット（Playwright が生成・上書き）
pwa/src/manual/generated/         ビルド生成物（本文 HTML・トピック ID 型・ルート対応表）
```

- ページ分割の軸は **1 ページ = 1 画面**（`pwa/src/pages/*` と 1:1）とし、その上に複数画面をまたぐ**タスク横断章**（初回セットアップ、チェックアウトの流れ 等）を重ねる。
  - 画面と 1:1 にすることで、「今見ている画面の『？』ボタン」が必ず行き先を持ち、スクリーンショット撮影と陳腐化追跡も画面単位で素直に対応する。
  - ロール（管理者／編集メンバー／活動メンバー）による見え方の差は、ページを分けず**ページ内の注記**で吸収する（上位ロールが下位を包含する既存仕様のため、ロール別に分けると同じ説明が重複して更新漏れの温床になる）。
- 多言語は **ja のみ**を執筆し、ディレクトリ構造・ビューア・生成スクリプトだけを locale 対応にしておく。`en` 追加時はディレクトリを増やすだけで済む。未訳ページは `ja` にフォールバックする。

## frontmatter スキーマ

```yaml
---
id: map                        # トピック ID（安定・ファイル名やパスと独立）
title: 区域編集（地図）
route: /map                    # 対応するアプリのルート（無い場合は省略）
status: draft | published      # draft = 本文未執筆／執筆途中
sources:                       # このページが説明している実装・仕様
  - pwa/src/pages/MapPage.tsx
  - docs/wants/03_地図機能.md
digest: a1b2c3d4e5f6           # 上記 sources の内容ハッシュ（機械が更新）
---
```

- `id` はマニュアル全体で一意。**リネームしても `id` を変えなければアプリ側のリンクは壊れない**。
- `sources` に挙げたファイルの内容から `digest` を計算する。実装を変えると digest がずれ、そのページが **stale（要更新）** として検出される。

## 本文中の特殊記法

いずれも機械が実体の存在を検査する。実体が消えていればビルド／検査でエラーになる。

| 記法 | 意味 |
|---|---|
| `{{shot:map-overview}}` | スクリーンショットの埋め込み（行頭に単独で置く。`\|` に続けてキャプション） |
| `{{topic:visits}}` | 他マニュアルページへの相互リンク（表示名は相手の `title`） |
| `{{route:/map}}` | アプリのルート表記（`pwa/src/App.tsx` に実在するか検査） |

## トピック ID の型生成（リンク切れ防止）

ビルドが全ページの `id` から union 型を生成する。

```ts
export type ManualTopic = "dashboard" | "map" | "visits" | ...;
```

アプリ側からマニュアルへ飛ぶ導線は **`<ManualLink topic="map" />` 経由のみ**とし、トピック ID を文字列で直接組み立てない。
これにより、マニュアルページを削除・改名して ID が消えると **`tsc` がコンパイルエラーで落ちる**（`npm run build` は `tsc &&` から始まる）。
リンク切れは「気づく仕組み」ではなく「通らない仕組み」で防ぐ。

## アプリ内での閲覧

- WebView ではなく通常ルート `/manual`（目次）・`/manual/:topic`（各ページ）で表示する。PWA 自体が Web のため別ウィンドウは不要。
- 本文もスクリーンショットも `dist` に同梱され、vite-plugin-pwa が precache する。**訪問先などオフライン環境でも閲覧できる**こと（本アプリの利用状況上これは必須要件）。
- 共通レイアウトのヘッダに「？」ボタンを置き、現在のルートに対応するトピックへ直行する。対応が無い画面は目次へ落とす。
- 開発ビルドでのみ、stale／draft のページに警告バッジを表示する。

## 陳腐化の検知と更新フロー

1. 実装を変更してコミットしようとすると、`.githooks/pre-commit` が `sources` 経由で影響するマニュアルページを指摘する。
   - `sources` に挙がったファイルが**削除・改名**された場合はコミットをブロックする（機械的に確実な不整合のため）。
   - 内容の**修正**のみの場合はブロックせずリマインドする（責務が変わっていなければ更新不要なため）。
2. `npm run manual:check` で stale／draft／参照切れ／マニュアル未整備の画面を一覧する。
3. `.claude/skills/manual-sync` が stale ページを拾い、該当 `sources` の差分を読んで本文を更新する。
4. `npm run manual:shots` でスクリーンショットを撮り直す。
5. `npm run manual:seal` で digest を現状に固定し、stale を解消する。

## スクリーンショットの自動撮影

- Playwright が起動前に `addInitScript` で固定のデモデータを localStorage へ流し込み、全画面・主要ダイアログを撮影する。
  - **アプリ側にデモシード用のコードは置かない**。当初は `?seed=manual` 起動モードを設ける想定だったが、
    アプリのデータは全て localStorage に決まった形で永続するため、撮影スクリプト側から書けば同じ状態を作れる。
    アプリ本体に一切コードを足さなければ、デモデータが本番バンドルへ混入する経路が構造的に存在しなくなる。
  - デモデータは専用のグループスロット（`hvs.g.<slotId>`）に書くため、開発者の手元の実データを壊さない。
- この方式は localStorage の保存形式に結合する。形式が変わると**無言で空の画面を撮る**という危険な失敗をするため、
  各ショットは撮影前に「そこに写っているべき文言」の表示をアサートし、外れたら撮影を失敗させる。
  形式ドリフトを黙って通さないことが、この結合を許容できる条件である。
- デモデータは実データに依存しないため、撮影結果が毎回同じになり、差分レビューでも意味のある変化だけが見える。
- 撮影対象（画面・到達手順・アサート文言・出力ファイル名）はスクリプト内の宣言的なリストとして持ち、画面追加時はそこへ 1 エントリ足すだけにする。

### 撮影環境の前提

いずれも実際に「無言で壊れた図」を生んだ事象への対処である。

- **絵文字フォントが要る**。アプリは ➕ ✂ 👁 🔒 🗑 等を UI に使う。ヘッドレス Chromium の
  既定環境には絵文字フォントが無く、豆腐（□）で撮れてしまう。WSL では Windows の
  `seguiemj.ttf` を `~/.local/share/fonts/` に置いて `fc-cache` すればよい。
- **等倍で撮る**。`deviceScaleFactor: 2` では Chromium の HiDPI 合成バグで、ボタンの文字が
  画面左端に二重に描かれる（DOM 上の位置は正しい）。鮮明さより図の正確さを優先する。
- **フォント読み込みを待つ**。`document.fonts.ready` を待たずに撮ると文字が抜けた画像になる。
  DOM には文言があるためアサートは通ってしまい、検知できない。
- **ヒントの吹き出しは UI から閉じる**。ヒント既読は個人設定であり、`VITE_LINKSELF=1` のときは
  LinkSelf の MyDB（OPFS SQLite）に入るため localStorage へのシードでは消せない。
- **`VITE_LINKSELF=1` ではシードが移行経由で効く**。ドメインデータは SQL 側にあるが、起動時に
  「SQL が空なら旧 localStorage から一度きり移行する」処理が走るため、撮影用の localStorage
  シードはこの移行に乗って反映される。したがって
  `src/data/linkself/legacy-group-data-migration.ts` の移行対象に入っていないテーブルは
  シードしても画面に出ない。出ないものを見つけたら、まず移行漏れを疑うこと
  （feedback がこれで漏れており、旧データが消える不具合として 2026-07-20 に判明した）。

## 既知の限界

- **画面文言の変更は陳腐化として検知されない**。マニュアル本文は i18n catalog（`pwa/src/i18n/ja/index.ts`）の文言を
  かぎ括弧で引用するが、この 1 ファイルを全ページの `sources` に入れると、どこか 1 語の変更で全ページが一斉に stale になる。
  常に鳴る警報は無視されるようになるため、あえて `sources` に含めない。
  文言だけを変えたときはマニュアルの引用が古くなり得る点は、人が意識して補う。
- **`manual:seal` は本文を読まなくても実行できる**。見直さずに seal すると古い本文へ「最新」の印がつき、
  以後その陳腐化は永久に検知されない。運用上の唯一の弱点であり、`manual-sync` スキルで手順として縛る。

## 検査項目（`manual:check`）

| 種別 | 内容 |
|---|---|
| エラー | `sources` に存在しないパス／`{{topic:}}` `{{shot:}}` `{{route:}}` の参照先が存在しない／`id` の重複 |
| 警告 | digest ずれ（stale）／`status: draft`／マニュアルページを持たないアプリのルート／参照されていない孤児スクリーンショット |
