# メンバー管理と権限

## メンバー管理機能

- LinkSelfグループ内におけるロール
  - 管理者
  - 編集メンバー
  - 活動メンバー（LinkSelfグループメンバー）
- メンバー権限は上位互換とする
  - 強い権限を持つメンバーは下位メンバーの権限を包含する
- 管理メンバー向けアプリには編集メンバー以上の権限を持つメンバーがログインできる。

## 初回オンボーディングと創設メンバー

- 最初にアプリを使うユーザーは、まず自分の ID（identity / DID）を作成する（`01_共通基盤.md`「自分の ID の作成と保管」）
  - 最初のユーザーは新しい LinkSelf グループの**創設者となり、ロールは管理者**とする（管理者0人状態を作らないため）
  - 以降のメンバーは招待経由で参加する（本ファイル「招待と任免」）
- 既に自分の ID を持つユーザーは、別端末を「自分のデバイス」として追加できる（`01_共通基盤.md`「端末ペアリング」）。追加された端末は同一 DID・同一ロールで動作する（別メンバーの追加ではない）
- **初回系画面のブランディング**: 初回オンボーディング・グループ参加（`#/join`）・端末引き継ぎ（`/pair`）の各画面には**アプリのロゴとアプリ名（Home Visit Suite）を表示**する（何のアプリか分からない無地の入力画面にしない）。アプリ名は固有名詞のため翻訳しない

## グループ名

- **LinkSelf 自体にはグループ（ネットワーク）名の概念は無い**（`Network` は id・suiteId・メンバー・ロール表のみ）。グループ名は **home-visit-suite アプリレベルのデータ**として持ち、LinkSelf のワイヤ形式には手を入れない
- **設定**: 創設者（初回オンボーディングで「新しく ID を作成する」を選んだユーザー）が **ID 作成時にグループ名を入力**する（必須）
- **変更**: 管理者はメンバー管理画面（`/users`）でグループ名をいつでも変更できる
- **保存**: 各端末のローカル（localStorage `hvs.groupName`）。**他メンバー端末への改名の伝播は ScopeNetwork 同期（link-self Phase C）待ち**。それまでの共有経路は招待 URL（下記）のみ——参加時点のグループ名が被招待者端末に保存され、以後の改名は届かない（既知の制約）
- **招待 URL への同梱**: 招待発行時、その時点のグループ名を招待 URL に**表示用パラメータ**（`&g=`、URL エンコード）として同梱する。被招待者は参加前でグループのデータを一切持たないため、参加画面での表示にはこの経路が唯一。署名対象（invite claims）には含めない**表示専用**の値であり、改竄されても参加先ネットワーク・ロールには影響しない

## 管理者権限

### 任免（メンバーの編集と削除）

- **2026-07-14 改訂: 任命招待（対象の受理で成立）フローは廃止**し、管理者による**直接変更**に統一する
  - 理由: 非同期参加で確立した「管理者の承認は操作時点で完結・受理フローを挟まない」思想と一貫させる。ScopeNetwork 未実装の現状では任命招待を対象に届ける通知経路も無い
  - 新規参加者を最初から上位ロールで迎える場合はロール付きグループ招待（下記「グループ招待」）を使う
- **メンバーの編集**（管理者のみ・メンバー管理画面 `/users` の各メンバー行から）
  - **表示名とロールを直接変更**できる（昇格・降格とも即時成立。対象の受理は不要）
  - ガード:
    - **自分自身のロールは変更不可**（管理者0人の状態を防止。自分の表示名変更は可）
    - **最後の管理者の降格は不可**（管理者が2人以上いる場合のみ他の管理者を降格できる）
    - **同名の禁止**: 既存メンバーと同じ表示名への変更はエラー（`01` 「表示名の変更」）
  - 旧仕様の「罷免時のレベル指定（降格）」は編集でのロール変更に対応する
- **メンバーの削除**（管理者のみ・同画面から）
  - 削除 = **LinkSelfグループからの削除**（LinkSelf ネットワークからの除名 + アプリのメンバー表からの削除）
  - **自分自身は削除不可**（自己罷免不可の原則。操作者が管理者である以上、他者削除で管理者0人にはならない）
  - 削除確認ダイアログで対象の表示名を示して確認する
- **LinkSelf 連携**: ロール変更・削除は LinkSelf ネットワーク実体（`memberRoles` / `members`）にも反映し、管理者として membership snapshot（`network_meta`）を配信する。オンラインのメンバー端末は LWW で収束する
  - **除名されたメンバー自身の端末には snapshot が届かない**（配信先は除名後のメンバー一覧のため）。当人の端末上の表示は残るが、以後の管理者側検証では非メンバーとして扱われる（既知の制約。通知は ScopeNetwork / 通知基盤で将来改善）
  - アプリのメンバー表と LinkSelf 実体が対応しないレコード（開発シード等）は**アプリ側のみ更新**する（LinkSelf 同期は best-effort。`target_not_member` / `network_not_found` は許容）
- 強権管理者が相互闘争状態になる最悪の状況を想定する必要もあるが、現時点では深くは検討しない

### グループ招待（URL / QR による参加）

- **他のユーザー（別 DID）をグループに参加させる**招待。デバイスペアリング（同一 DID の別端末追加）とは別物で、被招待者は自分の identity を保ったまま参加する（**秘密鍵は運ばない**）。
- 発行は**メンバー管理画面（`/users`）から、管理者のみ**が行える（活動メンバー・編集メンバーには発行 UI を表示しない）。招待を作成し、**URL を送る／QR コードを渡す**。被招待者はブラウザで URL を開く（`#/join?i=...`）と参加フローに入る。
- **発行時にロールを指定できる**（管理者・編集メンバー・活動メンバーから選択。**既定は活動メンバー**）。ロールは署名付き招待 claims に含まれ、参加成立時にそのロールで成立する。発行ダイアログには選択したロールを表示する（渡し間違い防止）
  - ロール付き招待は「招待と任免」の任命招待（既存メンバーへの昇格）とは別物——**新規参加者を最初から編集メンバー／管理者として迎える**ためのもの
- **トークン期限は 3 日**（デバイスペアリングは数分。後日ブラウザで開く運用のため長め）。期限切れ・改竄・単回使用済みの招待は拒否される。
- 参加すると**招待に含めたロール**で成立する（既定は活動メンバー）。**参加成立時に被招待者のローカルロールも招待ロールへ更新**する（創設オンボーディングの「最初のユーザー = 管理者」規則は招待参加には適用しない）。
- **参加画面の表示**: アプリのロゴ・アプリ名とともに**「「○○」グループに招待されています」**（○○ = 招待 URL 同梱のグループ名。本ファイル「グループ名」）を表示する。グループ名が同梱されていない旧招待では汎用文言にフォールバックする。参加成立時にグループ名を被招待者端末へ保存する。
- **ID 未作成の端末での参加（ワンストップ）**: 招待 URL を開いた端末に ID が無い場合も、同じ画面の表示名入力から「ID を作成して参加」で一気に完了する（ID を活動メンバーとして作成 → 自動で参加継続。別画面での ID 作成や URL の再アクセスは要求しない）。
- 実体は LinkSelf の**ネットワーク招待プロトコル**（署名付き capability → 参加ハンドシェイク → メンバーシップ伝播）。被招待者は管理者へ（リレー経由で）到達して招待を提示し、管理者が検証してネットワークに追加、被招待者は応答スナップショットからグループに参加する。設計 SoT: `link-self/docs/spec/network-invitation.md`。
  - ブラウザ同士は着信不可のため**常時稼働ノード（リレー）**が必要（`docs/wants/11 §2`・`VITE_LINKSELF_RELAYS`）。
- **参加受理時のメンバー表への記録**: 参加リクエストの表示名は**受理した管理者にしか見えない**ため、受理と同時にその管理者の端末で User（DID・表示名・招待ロール）をメンバー一覧（`/users`）へ登録する（LinkSelf の `onMemberJoined` フック経由。再参加では既存のタグ・参加日時を保持）。**表示名が既存メンバーと衝突する場合は「名前(2)」から始まる連番を付けて登録する**（(2) も使用済みなら (3)…。参加自体は妨げない。本人の端末上の自称は変わらず、受理側メンバー表の表記のみ）。**他メンバー・他端末の一覧への伝播は ScopeNetwork 同期（link-self Phase C）待ち**であり、それまでは受理した管理者の端末のみに表示される。
- **ライフサイクル**: ノードは**タブが開いている間**稼働する（停止はページ破棄 pagehide のみ。非表示 hidden では停止しない——デスクトップでは別ウィンドウに隠れただけで hidden になり受理待ちが成立しないため）。管理者がオフラインの間の参加は非同期参加（下記）で成立する。
- **非同期参加（メールボックス経由・2026-07-14 実装）**: トークン寿命 3 日の間、管理者が常にオンラインである必要はない。**承認は招待の発行時に済んでいる**（署名付き capability が唯一の承認。被招待者が受け入れた時点で参加は確定し、管理者が改めて承認し直すフローは存在しない）。参加時はまず同期参加（管理者へ直接到達→即時成立）を試み、**届かない場合は常時稼働ノードのメールボックスに封緘済み参加リクエストを預ける**。以後は管理者側アプリがオンラインになった時点で自動的に成立する。
  - **被招待者側 UX**: 預けたら「参加を受け付けました（自動で完了します）」を表示し、タブを閉じてよい。参加状態（招待と表示名）は端末に保存され、次回以降アプリ（または招待 URL）を開いたときに自動で結果を確認する。成立していれば参加完了（招待ロールを自ロールに採用）、招待が失効していれば失効を表示する。
  - **管理者側**: 操作は一切不要（完全無人・自動）。アプリ起動時と稼働中の定期ポーリング（60 秒）でメールボックスを確認し、届いていた参加リクエストを検証してメンバー表へ記録し（同期参加と同じ経路）、封緘済みの成立結果（グループのスナップショット）を被招待者宛に預け返す。管理者端末を経由するのは**メンバー表が各メンバー端末にしか存在しない**（サーバーレス P2P）ための技術的な中継であり、追加承認ではない。
  - **安全性**: 封筒はメールボックス（常時稼働ノード）が読めない E2E 封緘（招待 capability・表示名を秘匿。「ただの土管」原則維持）。リクエストは被招待者の署名で DID を束縛（同期参加の transport 認証と等価）、受理結果は**招待発行者の署名がある場合のみ**受け入れる。重複リクエストは既にメンバーなら参加成立を再送する（受理結果封筒の期限切れ救済）。
  - プロトコル設計 SoT: `link-self/docs/spec/network-invitation.md` §7（メールボックス `/linkself/mailbox/1.0.0` は常時稼働ノードの `enableMailbox` で提供）。
- 罷免時の進行中データの扱い
  - 活動メンバーへの降格：チェックアウトの担当者としては継続できる
    - 編集メンバー時代に自分自身を担当者にしてチェックアウトしたデータ（`PersonInChargeID == CheckedOutByID`）もそのまま継続する
    - `CheckedOutByID` は当時の操作履歴として保持し、降格に伴う書き換えはしない（監査ログ的な扱い）
    - 当該チェックアウトに紐づく未失効の区域招待もそのまま有効。発行済み招待の取消権限（招待者本人＝降格後の本人）は維持される
  - LinkSelfグループからの削除：担当者なしになる。未処理タスクも担当者なしになる

## 領域・区域の管理権限

- 領域の管理（追加・編集・削除・並べ替え）は管理者専用ページで行う
  - 左サイドバーの「領域管理」からアクセスする
  - 管理者が領域を定義する（名称と記号の指定。この時点では概念上のデータ）
  - 領域の編集はモーダルで名称・記号を変更できる
    - 記号変更時は配下への影響を警告表示する
  - 領域の表示順は上下ボタンで変更する（ドラッグ&ドロップではない）
  - 領域の削除は確認ダイアログで名称と記号の両方を入力させ、一致した場合のみ削除可能とする
  - ポリゴン作成などの実作業は編集メンバーが行う
- 地図ページの右サイドバーでは領域は閲覧のみ
  - 区域親番・区域の追加・編集・削除は右サイドバーで編集メンバーが行う
- 領域内の区域親番・区域の作成は編集メンバーが行う
- 承認フロー
  - 一そろいの領域内区域が完成した時点で管理者が承認する
  - 承認後は編集メンバー権限では区域・区域親番の削除ができなくなる
  - 削除を伴わない編集（境界ポリゴンの修正など）は承認後も編集メンバーが行える
    - 境界頂点の編集はマップポリゴンライブラリでバリデーションするので不整合にはならない
  - 承認済みの領域に区域を追加する場合は再承認が必要
- 領域・区域親番・区域の削除は管理者のみが可能

## メンバー分類の方針

- App 内に「メンバーグループ（OrgGroup）」概念は持たない（廃止済み）
- メンバーの分類は **ロール（管理者・編集メンバー・活動メンバー）** と **メンバータグ** のみで表現する
- 「Aチーム／Bチーム」のような運用上のチーム分けが必要な場合はメンバータグで運用する（タグ管理は管理者専用、後述）
- 編集メンバーは LinkSelf グループ全体に対して権限を行使できる（チーム単位の壁はシステムでは設けない）

## メンバータグ機能

- 位置づけ：システム内の権限とは厳格に紐づかないが「この人は○○係」というような共通認識として運用するラベル
- **タグ管理は管理者専用**（メンバー管理権限の一部として扱う）。メンバー管理画面 `/users` 内で完結する。編集メンバーはタグの作成・編集・付与・削除権限を持たない

### タグの作成・管理

- 管理者がタグを作成できる
- 入力方式：既存タグ一覧からの選択＋新規タグのその場作成（両対応）
- タグ名は最大16文字
- 同名タグの重複作成は禁止
- タグの編集（名前変更）・削除は管理者のみ可能

### タグの色

- タグには色を設定できる
- 作成時にシステムが自動で色を割り当てる
- 管理者が後から色を変更できる

### タグの付与

- 管理者が他のメンバーにタグを付与できる
- 1メンバーあたりのタグ上限は10個

### タグの削除

- タグを削除する際、そのタグが付いている全メンバーから外れる旨の確認ダイアログを表示し、承認後に一括削除する

### タグの表示

- メンバー一覧およびメンバー詳細画面にタグを表示する
- メンバー一覧ではタグによるフィルタリング（絞り込み）が可能
- 編集メンバーは `/users` ページにアクセスできないため、タグを直接閲覧する経路は持たない（必要なら他画面に閲覧用 UI を別途検討）

### 活動メンバーからの見え方

- 活動メンバーは自分に付けられたタグを確認できる（閲覧のみ）
- 活動メンバーはタグの追加・変更・削除はできない
