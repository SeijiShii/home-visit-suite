# メンバー管理と権限

## メンバー管理機能

- LinkSelfグループ内におけるロール
  - 管理者
  - 編集メンバー
  - 活動メンバー（LinkSelfグループメンバー）
- メンバー権限は上位互換とする
  - 強い権限を持つメンバーは下位メンバーの権限を包含する
- 管理メンバー向けアプリには編集メンバー以上の権限を持つメンバーがログインできる。

## 初回オンボーディングと創設メンバー

- 最初にアプリを使うユーザーは、まず自分の ID（identity / DID）を作成する（`01_共通基盤.md`「自分の ID の作成と保管」）
  - 最初のユーザーは新しい LinkSelf グループの**創設者となり、ロールは管理者**とする（管理者0人状態を作らないため）
  - 以降のメンバーは招待経由で参加する（本ファイル「招待と任免」）
- 既に自分の ID を持つユーザーは、別端末を「自分のデバイス」として追加できる（`01_共通基盤.md`「端末ペアリング」）。追加された端末は同一 DID・同一ロールで動作する（別メンバーの追加ではない）

## 管理者権限

### 招待と任免

- 他の管理者を任免する
  - 管理者は自己罷免不可とする（管理者0人の状態を防止）
  - 罷免は強制即時罷免とする
  - 強権管理者が相互闘争状態になる最悪の状況を想定する必要もあるが、現時点では深くは検討しない
  - 任命
    - 編集メンバーに任命招待を送る。
    - 編集メンバーが受理すると成立する。
  - 罷免
    - 罷免時にレベルを指定する。
      - 編集メンバーへの降格
      - 活動メンバーへの降格
      - LinkSelfグループからの削除
- 編集メンバーの任免
  - 任命
    - 活動メンバーに任命招待を送る
    - 活動メンバーが受理すると成立する
  - 罷免
    - 罷免時にレベルを指定する。
      - 活動メンバーへの降格
      - LinkSelfグループからの削除
- 活動メンバーの任免
  - 任命
    - LinkSelfグループ招待
    - 招待を受理すると成立する
  - 罷免
    - LinkSelfグループからの削除

### グループ招待（URL / QR による参加）

- **他のユーザー（別 DID）をグループに参加させる**招待。デバイスペアリング（同一 DID の別端末追加）とは別物で、被招待者は自分の identity を保ったまま参加する（**秘密鍵は運ばない**）。
- 発行は**メンバー管理画面（`/users`）から、管理者のみ**が行える（活動メンバー・編集メンバーには発行 UI を表示しない）。招待を作成し、**URL を送る／QR コードを渡す**。被招待者はブラウザで URL を開く（`#/join?i=...`）と参加フローに入る。
- **トークン期限は 3 日**（デバイスペアリングは数分。後日ブラウザで開く運用のため長め）。期限切れ・改竄・単回使用済みの招待は拒否される。
- 参加すると **活動メンバー**として成立する（ロールは招待に含めた値。既定は活動メンバー）。
- 実体は LinkSelf の**ネットワーク招待プロトコル**（署名付き capability → 参加ハンドシェイク → メンバーシップ伝播）。被招待者は管理者へ（リレー経由で）到達して招待を提示し、管理者が検証してネットワークに追加、被招待者は応答スナップショットからグループに参加する。設計 SoT: `link-self/docs/spec/network-invitation.md`。
  - ブラウザ同士は着信不可のため**常時稼働ノード（リレー）**が必要（`docs/wants/11 §2`・`VITE_LINKSELF_RELAYS`）。
- **参加受理時のメンバー表への記録**: 参加リクエストの表示名は**受理した管理者にしか見えない**ため、受理と同時にその管理者の端末で User（DID・表示名・招待ロール）をメンバー一覧（`/users`）へ登録する（LinkSelf の `onMemberJoined` フック経由。再参加では既存のタグ・参加日時を保持）。**他メンバー・他端末の一覧への伝播は ScopeNetwork 同期（link-self Phase C）待ち**であり、それまでは受理した管理者の端末のみに表示される。
- **当面の制約（前景ライフサイクル）**: ノードはタブ前景時のみ稼働するため、**受理する管理者はタブを表示したまま**にする必要がある（タブ非表示→graceful stop で管理者に到達できず参加が失敗する。復帰時の自動再起動は未実装の実装課題）。
- 罷免時の進行中データの扱い
  - 活動メンバーへの降格：チェックアウトの担当者としては継続できる
    - 編集メンバー時代に自分自身を担当者にしてチェックアウトしたデータ（`PersonInChargeID == CheckedOutByID`）もそのまま継続する
    - `CheckedOutByID` は当時の操作履歴として保持し、降格に伴う書き換えはしない（監査ログ的な扱い）
    - 当該チェックアウトに紐づく未失効の区域招待もそのまま有効。発行済み招待の取消権限（招待者本人＝降格後の本人）は維持される
  - LinkSelfグループからの削除：担当者なしになる。未処理タスクも担当者なしになる

## 領域・区域の管理権限

- 領域の管理（追加・編集・削除・並べ替え）は管理者専用ページで行う
  - 左サイドバーの「領域管理」からアクセスする
  - 管理者が領域を定義する（名称と記号の指定。この時点では概念上のデータ）
  - 領域の編集はモーダルで名称・記号を変更できる
    - 記号変更時は配下への影響を警告表示する
  - 領域の表示順は上下ボタンで変更する（ドラッグ&ドロップではない）
  - 領域の削除は確認ダイアログで名称と記号の両方を入力させ、一致した場合のみ削除可能とする
  - ポリゴン作成などの実作業は編集メンバーが行う
- 地図ページの右サイドバーでは領域は閲覧のみ
  - 区域親番・区域の追加・編集・削除は右サイドバーで編集メンバーが行う
- 領域内の区域親番・区域の作成は編集メンバーが行う
- 承認フロー
  - 一そろいの領域内区域が完成した時点で管理者が承認する
  - 承認後は編集メンバー権限では区域・区域親番の削除ができなくなる
  - 削除を伴わない編集（境界ポリゴンの修正など）は承認後も編集メンバーが行える
    - 境界頂点の編集はマップポリゴンライブラリでバリデーションするので不整合にはならない
  - 承認済みの領域に区域を追加する場合は再承認が必要
- 領域・区域親番・区域の削除は管理者のみが可能

## メンバー分類の方針

- App 内に「メンバーグループ（OrgGroup）」概念は持たない（廃止済み）
- メンバーの分類は **ロール（管理者・編集メンバー・活動メンバー）** と **メンバータグ** のみで表現する
- 「Aチーム／Bチーム」のような運用上のチーム分けが必要な場合はメンバータグで運用する（タグ管理は管理者専用、後述）
- 編集メンバーは LinkSelf グループ全体に対して権限を行使できる（チーム単位の壁はシステムでは設けない）

## メンバータグ機能

- 位置づけ：システム内の権限とは厳格に紐づかないが「この人は○○係」というような共通認識として運用するラベル
- **タグ管理は管理者専用**（メンバー管理権限の一部として扱う）。メンバー管理画面 `/users` 内で完結する。編集メンバーはタグの作成・編集・付与・削除権限を持たない

### タグの作成・管理

- 管理者がタグを作成できる
- 入力方式：既存タグ一覧からの選択＋新規タグのその場作成（両対応）
- タグ名は最大16文字
- 同名タグの重複作成は禁止
- タグの編集（名前変更）・削除は管理者のみ可能

### タグの色

- タグには色を設定できる
- 作成時にシステムが自動で色を割り当てる
- 管理者が後から色を変更できる

### タグの付与

- 管理者が他のメンバーにタグを付与できる
- 1メンバーあたりのタグ上限は10個

### タグの削除

- タグを削除する際、そのタグが付いている全メンバーから外れる旨の確認ダイアログを表示し、承認後に一括削除する

### タグの表示

- メンバー一覧およびメンバー詳細画面にタグを表示する
- メンバー一覧ではタグによるフィルタリング（絞り込み）が可能
- 編集メンバーは `/users` ページにアクセスできないため、タグを直接閲覧する経路は持たない（必要なら他画面に閲覧用 UI を別途検討）

### 活動メンバーからの見え方

- 活動メンバーは自分に付けられたタグを確認できる（閲覧のみ）
- 活動メンバーはタグの追加・変更・削除はできない
